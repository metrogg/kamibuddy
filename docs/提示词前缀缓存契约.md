## 读法（先看这条，否则会照抄错东西）

dsh 的完整方案（in-history 追加）**依赖一条模型契约**：「模型接受任意位置的
`system` 消息，并把最新那条当作完整系统提示词，替换掉 leading 那条」。这条契约
在我们这条 OpenAI 兼容端点上**没有复现**（spec 的「探针结论③」实测）。所以本文
对我们的价值不是「照抄机制」，而是**纪律与账法**：什么事实不许进前缀、变更怎么
记账、计量为什么允许不准、门禁怎么钉住。逐条列在下面，每条末尾给 dsh 来源路径。

## 一、契约要点

### 1. 提示词一变，整段前缀缓存作废

**契约**：provider 的前缀缓存比的是最长公共前缀；系统提示词是请求的 message 0，
它内部任何一个字节变化，都会让该请求从第一个 token 起 cache miss —— 代价随对话
历史长度放大，长会话反复付。所以「把变化的事实移出提示词」是保住前缀的**唯一**
办法（原文结论：moving a changing fact out of the prompt was the only way to keep
the prefix stable）。

**我们的对应物**：`src/core/system-prompt-composer.ts` 文件头（「会话内字节稳定」
与「逐轮可变」的两分类纪律）、`src/extensions/prompt-switch.ts` 文件头的三条判据
(a)(b)(c)、以及 spec Why 段的台账实测（6 会话首调只命中 1,408–2,816 / 12K–22K）。

**差距**：无。这是我们已落地的核心纪律。

**来源**：`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（Problem 段）

### 2. `PromptContext` 是 `PromptSection` 的 cache-safe counterpart

**契约**：`PromptSection` 是**静态**提示词分段（按 order 升序拼接，注册在进程内，
可 `complete` 独占整篇）；`PromptContext` 是**动态**内容的对应物 —— 组装时同样解析
与排序，但 agent-loop 把它的**完整当前快照**记成一条 **durable user-role 消息**，
**追加在保留的模型历史之后**，且**只在它变化（或被压缩移除）时才记**。注册项
空文本不贡献任何东西。

**我们的对应物**：三方合起来等价于「动态内容单独走一条落历史之后的通道」：

- `src/core/prompt-composer.ts` 的 `formatRuntimeContext`（记忆内容 / 个性化的纯函数实现）；
- `src/extensions/prompt-switch.ts` 的 `context` handler —— 追加在消息数组**末尾**
  （= 历史之后），`role:"custom"` / `customType:"kamibuddy-runtime-context"` / `display:false`；
- `src/core/session-host.ts` 的 `composeRunHiddenContext` + `installHiddenContext`
  （`prependHiddenContext` 把 `workspace_context` / `memory_and_skills_reminder` /
  `current_time` 贴到最后一条 user 消息内），契约层在 `src/shared/hidden-context.ts`
  （`composeHiddenContext` / `wrapHiddenContextXml`，容器契约 = `data-role` 属性）。

**差距（这一条差得最多）**：

- 我们是**每请求现算、不落盘**（`context` 返回值不写会话文件），所以 dsh 的
  「只在变化时记录」在我们这里**无事可做**：不落盘就没有沉积、没有陈旧清理
  （他们要为被遮蔽的旧节点逐条记 empty replacement，我们不需要）。代价是我们把
  dsh 的账法「model-visible ⟺ logged」只做到**指纹级**：`request_snapshot` 记
  `messageList`（id / chars / tokens / fp，**不落正文**）与 `hiddenContextChars`，
  模型实际读到的注入正文不进台账、事后只能从当轮的重算复现。
- 我们没有 registry 那一套：无段序集中分配（`getContextOrder`）、无作用域遮蔽
  （scope shadowing）、无 `suppressRuntimeContext()`；三段顺序是硬编码的。
- 他们是**一个** `PromptContext` 概念；我们实际有**两个注入通道**（hidden context
  贴在最后一条 user 消息内、runtime context 追加在消息数组尾部），属历史沿革而非设计。

**来源**：`…/docs/subsystems/system-prompt.md`（Dynamic prompt context 段）

### 3. 系统提示词以 surface node（node 0）进入 derived history，不是请求字段

**契约**：渲染后的提示词被提交成一个 `system/message` 的 **surface node**：第一步
作为 **node 0** 追加，之后按规则**原地替换**（或被追加，见 §5）。即系统提示词以
**消息**形态进入模型的 derived history，**不是**请求上的一个字段 —— 于是「提示词
变化」变成「对 surface 上 system 节点的操作」，读取方（transcript / 面板 / 计量）
都要**折叠 surface、取最新那条存活 system 节点**来回答「模型看到了什么」。

**我们的对应物**：`src/extensions/prompt-switch.ts` 的 `before_agent_start` 返回
`systemPrompt` 字符串（pi 0.85.1 的 forced 整串替换），pi 把它写成 leading system
消息；「模型看到了什么」由 `prompt-preview.ts` 的 `assembleSystemPrompt` 复用同一
产物回答（与真实组装同函数，见 spec 后续-A）。

**差距**：我们没有 surface / node 模型 —— 没有 node 0 头部保护、没有 per-node
commit 与投影、也没有一条「系统提示词被替换/追加」的会话事件；`request_snapshot`
里只有 `systemSegments`（分段 source + 字符数）这一种描述。**当我们升级到带
sections 的 pi 时，第 2 条（只有 sections、没有 node 与投影）会成为先决约束。**

**来源**：`…/docs/subsystems/system-prompt.md`（Prompt sections 段末）与
`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（Problem 第 3 段）

### 4. `SystemPromptUpdate = 'in-history'` 是**按路由声明的能力位**

**契约**：能力位定义在 LLM 层，作为可选兄弟字段 `systemPromptUpdate` 挂在
「已解析模型信息」与「已备好的调用」上；非法取值在加载时响亮拒绝。adapter 目录
按模型逐条声明（内置只有 `deepseek-flash` 声明它有），**缺席 = 该模型必须重写
message 0**。协议族与模型名不隐含支持：换 deployment 换目录即可，`pi-ai` 路由一律
保持 replace 行为。循环把实际生效的模式记进会话（`request/context` 的
`systemPromptUpdate` 字段），准入读的是 `agent/request` + `prepareCall()` **之后**
那条真实调用的字段 —— 首请求、resume、换路由、能力变更都用「真正服务这次调用的
adapter」的能力，不用上一次的快照。

**我们的对应物**：无能力位。我们的路线由**发布版 pi 的形态**决定（无 sections 路径，
只能 forced 替换），并被测试反向钉住：`src/extensions/prompt-switch.test.ts` 的
「返回值必须含 `systemPrompt`」用例（关掉就漏出 pi 默认 coding 提示词）。

**差距**：无 `in-history` 能力位、无 per-model 声明、无 `request/context` 模式字段。
**并且按我们的探针，这条能力位现在加了也不该用**：dsh 的模型契约在我们端点没复现
（见「读法」），加它属于照抄机制。将来升级 pi 时，复核入口见 spec 的
「将来升级 pi 时的复核入口」场景。

**来源**：`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（Capability 段）

### 5. 决策规则：追加还是重基线到 node 0

**契约**：每次调用扫描当前 surface 上**存活的** system 节点，返回有序的 per-node
commit；没有存活系统节点时**即便渲染为空也占住头部**；有效文本取自**最新非空**
system 节点，回落到头部；空渲染清掉所有活跃 system 节点（与路由/序列无关）。规则表
（按路由能力 × 前缀状态）：

| 路由能力 | 前缀状态 | 操作 |
| --- | --- | --- |
| 无（不能 in-history） | 任意 | 给每个非空的后继 system 节点记空替换，必要时重写第一个 system 节点 |
| `in-history` | 当前序列延续 | 在本步 `user/message` **之前**追加一条新的 `system/message`；追加本身不需要 `request/header` |
| `in-history` | 新序列开始 | **重基线**：给非空后继节点记空替换，必要时重写第一个 system 节点（**即便有效文本没变**） |
| 任意 | 渲染为空 | 记空替换，必要时清空头部；derived messages 里不再留有提示词版本 |

**我们的对应物**：我们的路线**等价于上表第一行（无能力列）** —— 文本变则重写
message 0（pi 内部按文本比对，未变就不产生替换，实测字节未变时首步命中 93.6%）；
文本不变则什么都不发。

**差距**：正因为「无能力」列**每次变化都重基线**，第 5/6 条里的序列判据、追加路径、
per-node 空替换在我们的路线上**整套用不上**；我们是靠「让文本别变」而不是靠
「变了也能追加」来保缓存。这是路线差异，不是缺陷，但升级 pi 时要重新过一遍这张表。

**来源**：`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（The decision rule 段）

### 6. `startsSeries` 的判据（含**可见工具集变化**）

**契约**：以下三种情况算「新序列开始」，必须重基线到 node 0：① `agent/pre-step`
决策显式声明 `startsRequestSeries`；② surface 的 replace generation 相对上次请求
变过（压缩或任何其他替换）；③ **可见工具 schema 集合变了**。而 **provider / model
换代本身不算序列开始** —— 能力路由上追加不额外花钱（换路由本来就丢缓存，重基线
省不出东西），于是不给循环加特例。

**我们的对应物**：无。我们没有序列概念（新会话 / resume / 压缩都只是发生），也没有
「工具集变化」这个触发点。

**差距**：同 §5 —— 在我们的「无能力」等价路线上，重基线是常态，所以这套判据暂时
没有落地位置。**值得记住的是判据③的方向**：工具 schema 也是缓存前缀的一部分，
工具集一变前缀同样作废（我们的工具白名单随模式变，属同类风险，只是当前由 pi 的
per-run 工具集决定）。

**来源**：`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（The decision rule 段第 2 段）

### 7. 追加节点的代价与账法

**契约**：`in-history` 追加的节点**在该序列里每请求都要付它自己的 token，直到被
压缩遮蔽**；因此原文的结论是：**提示词在多数步都会变的部署，更应该把这个事实移进
runtime context**，而不是靠追加。计量侧：`contextBreakdown.systemTokens` 只价
**surface 顺序里最后一个非空存活 system 节点**，其余可见节点（**含被取代的旧提示词**）
一律进 `messageTokens`；空休眠节点不计；三项之和恒等于启发式 surface 总量（含替换、
压缩、逐节点清空之后）。`cacheReadTokens` 只是「可观测到的 provider 缓存效果」。

**我们的对应物**：我们正是原文推荐的那种部署 —— 变化事实（记忆内容 / 个性化）
走**每请求现算的注入块**，不沉积成历史节点、不按序列重复付；时间走 hidden context
的 `current_time`（run 冻结）；`workspace_context` 提供 cwd。计量侧我们有
`estimateTokens`（`src/core/observability.ts`）与 `ContextComposition`
（`src/shared/observability.ts`，system / user / assistant / thinking / tools，
明确标注「估算」），另有 `billedInputTokens` / `cacheHitRate`（口径与 dsh 的
`cacheHitPercent` 一致，见该文件注释）。

**差距**：我们只有**一份**系统提示词、没有多节点，所以没有「只价最后一个存活
system 节点」这个语义，也没有「三项之和 = 启发式 surface 总量」这种自洽约束；
`cacheWaste`（missedTokens / missedCost / reason）是**浪费归因**，不是成分账。

**来源**：`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（Consequences 段）
与 `…/packages/llm/token-meter/README.md`（Session projections 段）

### 8. 被否决的备选方案（理由比结论更有用）

**契约**（否决理由，择要）：

| 备选 | 否决理由 |
| --- | --- |
| **只把变化的分段作为 delta 发出去** | 模型契约是「最新 system = 完整提示词」，delta 会**静默丢掉**所有未变化的分段 —— 依模型契约否决 |
| 用插件配置开关开启 in-history，而不是能力位 | 非能力模型会把追加的 system 当普通历史；能力属于「遵守它的那条路由」，不该由部署开关决定 |
| 永远追加、从不重基线 | node 0 会一直陈旧，压缩后每请求都同时背着陈旧头部与替换；序列开始处重基线不额外花钱（缓存本来就丢了） |
| 每次 resume 都重基线 | 缓存跨进程重启能活数小时到数天，不值为「resume 路径简单」付这一刀 |
| 把 system 消息放在本步 user 消息**之后** | 两个位置都在缓存前缀之后，但那样模型会先读到输入、后读到要施加于它的指令；system 在 user 前与 leading 位置的顺序一致 |
| 在 `agent/pre-step` waterfall **之前**做投影 | 看不到 waterfall 里刚做的压缩，可能本步就被遮蔽，请求只剩 node 0 的陈旧提示词；投影必须是「请求所依据的 surface」的纯函数 |
| 用**上一次**请求上下文做准入判断 | 它描述的是上一次调用，不是 request middleware 之后绑定的 adapter；首调用 / resume / 换路由 / 能力变更时会选错表示 |
| 把 provider / model 换代当作序列开始 | header 已记录变化、缓存两头都要丢，多这条规则只给循环添一个特例 |
| 只清最新的 system 节点 | 空节点投影为空消息，更旧的提示词会**复活**；清掉所有活跃版本才保住「空渲染」的语义 |

**我们的对应物 / 差距**：第 1 条正是我们**不能**走 sections/delta 路线的依据（可惜
我们依赖的 pi 也没有那条路，见 spec 探针结论①）；第 3/5/6 条是「升级 pi 后要不要改
路线」的复核清单。其余各条我们目前都无对应实现。

**来源**：`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（Alternatives considered 段）

### 9. 计量纪律：允许不准，但必须确定、可回放、多消费者读数一致

**契约**：文本与未声明图片价的路由用**固定启发式**（每 token 四字符 + 结构与角色
开销）；**明确承认**它严重低估 CJK 与 JSON schema；**刻意不做** per-provider 精确
tokenizer —— 理由是「保持一个确定性启发式，才能让每个消费者的测量一致、回放稳定」
（`Dev Note` 明写：per-provider exact tokenizer 未决，四字符启发式对 CJK / JSON
schema 低估，provider 锚定总量**恰好携带这份误差**）。`contextBreakdown`
（systemTokens / toolsTokens / messageTokens）是**成分**、不是 provider 计费量：
它**不会**等于按 provider 锚定的 `projectedTokens`，**差额就是启发式误差**；因此
成分行只能当近似成分呈现，**永远不能当总量**。provider 上报用量只在**同一规范
请求信封**下才被复用；替换（含系统提示词重写）在相邻计量事件里**带零影子价格**，
直到下一个成功调用的用量样本。

**我们的对应物**：`estimateTokens`（`src/core/observability.ts`：CJK 按约 1 token/字、
其余约 4 字符/token，注释要求诊断页必须标注「估算」——我们**对 CJK 做了补偿**，
与 dsh 的一刀切四字符不同）、`ContextComposition`（估算成分）、
`billedInputTokens` / `cacheHitRate`（与 dsh 口径一致，且注明「三桶之和」的分母理由）。

**差距**：我们**没有**写成纪律的东西有两条 —— ①「刻意不做精确 tokenizer」的理由
（我们只是没做，没记为什么，容易被后人当缺口去补）；②「成分估算不得与 provider
计费量并排相加 / 不得当总量」的红线（我们的 `ContextComposition` 有「估算」标注，
但没有「不等于 provider 锚定总量、差额即误差」这句显式约束）。两条都值得照抄。

**来源**：`…/packages/llm/token-meter/README.md`（Reading the numbers 段与 Dev Note）

### 10. 不反推缓存断点，而是把「变更」记成一等事实

**契约**：它的做法是**记账**而不是**反推** —— `request/header` 管配置与工具、
system 节点自己**带 update 标记**、`request/context` 记路由与模式；于是「这轮变了
什么」是日志里读出来的事实，`cacheReadTokens` 只被当作「provider 缓存的可观测效果」。

**我们的对应物（方向相反，如实记录）**：我们**既有**一半记账（`run_ledger` 的
`request_snapshot.systemSegments` / `messageList` / `hiddenContextChars`、
`cacheWaste` 的 `reason` 归因 idle_ttl / model_change / other），**又额外做了一个
反推器** `src/shared/cache-prefix.ts` 的 `inferCachePrefixBreak`（CACHE6）：先按
「上一轮 prompt 总量 − 上一轮消息估算总量」定标前缀，再按前缀累加与 `cacheRead`
对齐，超出与上一轮的**确定性**差异点时收敛并标 uncertain。

**差距（本文件里最值得记的方法论差异）**：我们缺少 dsh 的「header / context 变更
记录」这一层，所以**必须**靠估算对齐去补断点，`inferCachePrefixBreak` 的注释也
如实登记了「自带一个消息条数量级的误差、系统提示词内部断在哪一段指不出来」。
真要对齐 dsh，缺的是**变更事件**（配置 / 路由 / 工具集），不是更准的估算。这条路
我们**没有搬**，只把结论记下来。

**来源**：`…/packages/llm/token-meter/README.md`（Readings 与 Known Limitations 段）与
`…/.agents/notes/implemented/feature/2026-09-02-in-history-system-prompt-replacement.md`（Presentation and accounting 段）

### 11. 门禁做法：把「缓存效应」变成每个包的必填字段

**契约（可借鉴的机制）**：`scripts/verify-package-readme-model-experience.ts` 机械
校验**每一个包**的 README：必须有 `## Model Experience`，其下必须有 `#### KV Cache
effect` 且**非空**（结构化形态还强制 `#### What the model sees` / `#### Token
effect` 三段齐全且顺序固定，`## Model Experience` 与 `## Known Limitations and
Deferred Work` 必须是最后两个 H2）；简单包走白名单式「一句 + KV Cache effect」短式；
纯模型无关的包走 `NO_MODEL_EXPERIENCE_SECTION` 白名单，且**必须写明**为什么可以整段
缺席（「不能把缺席误当遗忘」）。于是同一句标准断言会在多个包重复出现，典型是：
「Append-only; newly visible content follows the reusable request prefix and does not
invalidate existing KV-cache entries.」差异化行为则写差异化条件（例如
「Prefix-stable while the registration scope and prompt text are unchanged」）。

**我们的对应物**：`npm run check`（typecheck + check:deps + check:tokens）里**没有**
文档门禁；我们的护栏是**更强的反向钉子**，落在
`src/extensions/prompt-switch.test.ts`：①「`before_agent_start` 必须返回
`systemPrompt`」；②「同会话系统提示词字节稳定」（work × code × 三种模式共 6 例，
只推进墙钟，断言两轮严格相等）；③「生产组装入口的产物不含任何时间/日期形态」。

**差距**：**我们的护栏钉的是「提示词」，dsh 的门禁钉的是「每个模块的缓存效应」** ——
后者能防住「新加一个模块，顺手往请求前缀里塞了变化内容」这类**跨模块**渗漏，我们
现在的钉子只覆盖系统提示词这一条路径。这条**未搬**，登记在此备用（要抄的话，
落点应在 `scripts/check-*.ts` 一侧而非文档）。

**来源**：`…/scripts/verify-package-readme-model-experience.ts`（顶层常量与校验分支；
各包 README 的 `#### KV Cache effect` 段，如 `…/packages/shell/tool-bash/README.md`）

## 二、对照结论

**已对齐（纪律层，行为等价或等价于更好的形态）**：

| # | 契约 | 状态 |
| --- | --- | --- |
| 1 | 变化事实不得进缓存前缀；移出去才是唯一解法 | ✅ 已落地（字节稳定纪律 + 注入通道） |
| 2 | 动态内容作为 append-only/落历史之后的快照送达 | ✅ 已落地（两个注入通道；**不落盘**是取舍） |
| 7 | 「提示词常变」的部署应把事实移进 runtime context | ✅ 我们正是这种形态 |
| 9 | 固定启发式、允许不准、标注估算、口径与 dsh 对齐 | ⚠️ 大部分对齐，两条纪律未写下来 |
| 11 | 门禁把不变量钉死 | ⚠️ 形态不同（钉提示词 vs 钉每个模块） |

**仍未对齐（差距，按重要级）**：

| # | 差距 | 影响 / 何时要补 |
| --- | --- | --- |
| 3 | 无 surface node / node 0 / system 节点投影 | 升级到带 sections 的 pi 时是**先决约束**（先有节点模型才谈得上追加） |
| 4 | 无 `in-history` 能力位与 per-model 声明 | 我们的探针显示该模型契约未在本端点复现，**暂不补**；升级 pi 时重评 |
| 5/6 | 无序列概念、无 `startsSeries`（含工具集变化）判据、无重基线规则 | 当前路线等价于「无能力列」（每次变化都重基线），暂时无处落地 |
| 2 | 无 PromptContext registry（段序 / 作用域 / suppress） | 段序现在硬编码；将来注入源变多时要收敛 |
| 2 | 「model-visible ⟺ logged」只到指纹级（注入正文不落台账） | 想事后严格复现「模型这轮读了什么」时是缺口 |
| 7 | 无 `contextBreakdown` 三分类与「和 = 启发式总量」自洽约束 | 面板成分口径只能靠单一系统提示词推算 |
| 10 | 没有「变更一等事实」（header / context 事件），因此要反推断点 | CACHE6 的估算对齐自带消息条数量级误差 |
| 11 | 没有跨模块的「缓存效应」门禁 | 新模块往前缀塞变化内容时不会变红 |

## 三、升级 pi 时的复核入口（一句话）

若依赖升到带 `sections` / 分段 patch 的版本：**先复跑 `npm run probe:prompt-cache`**，
用真实产物复核 dsh 那条模型契约（「中段 system = 完整系统提示词」）在我们端点上
是否成立 —— 探针结论③的保留意见是「手写 delta 的渲染形态可能与 pi 真实 patch 不同」，
成立与否直接决定 §8 第 1 条（delta 被否）能不能照搬。
