## 怎么用这份清单

1. **每行可独立开一个 spec**，编号即 spec 名（如「CTX6 上下文增量 diff」）。
2. **「参考实现」列写的是内部机制，不是界面描述。** 复刻时按这一列做，不要按印象做。
3. **状态列只反映代码里实际有的东西**，不反映文档里写过的计划。勾选前先看一眼证据。
4. **改上层不改下层**：记录层是事实源，投影层是派生，展示层是消费。
   要加一个界面，先确认下层有没有这个东西——没有就先补下层，不要在展示层造假数据。
5. 优先级建议在文末。

## 三层的分工（这是理解全表的钥匙）

```
记录层  logs/runs/<sessionId>.jsonl（运行台账，append-only，事实源）
        logs/events-YYYY-MM-DD.jsonl（daemon 事件日志）
        会话 JSONL（pi 的消息账本，含消息正文与 usage 明细）
            │  fold / 回放
投影层  ObservabilitySnapshot（daemon 算好，renderer 不二次计算）
        run-timeline（renderer 侧 fold 成泳道，形状天然是派生，不属聚合口径）
            │  消费
展示层  诊断页 / 会话时间线 / 聊天指标条 / 上下文圆环
```

**为什么不双写**：消息正文只在会话 JSONL 落一份，台账只记 pi 不记的东西
（计时/TTFT/重试/快照）。两份都写必然漂移——这是 `core/run-ledger.ts` 文件头
钉住的第一条纪律。

**提示词前缀稳定性（CACHE8 的基线与复跑口径，2026-09-17，spec: stabilize-prompt-prefix）**

**为什么它是结构性前提**：provider 的前缀缓存比的是最长公共前缀，而系统提示词位于**整段对话历史之前** —— 它里面任何一个字节的变化，都会让它**其后的一切（含整段历史）**在缓存里失配，代价随会话长度放大。「同一会话内系统提示词逐轮字节稳定」因此不是优化项，是命中率的前提。

**复跑入口与判据**：`npm run probe:prompt-cache`（真实 API，消耗极小额度；不进 `npm test`——单测不该打网络）。判据只看**同一条轮次序列内的差**，不看跨次绝对值：同一会话里「提示词字节完全不变」那一步的首调 hit 应显著高于「变更一处」那一步，稳态 ≥90%（2026-09-17 实测：字节不变 **93.2%** ／ 变更一行（84.8% 字符深度）**62.0%**）；第二轮首步 hit 明显高于 16% 才算改动生效。

**改动前台账基线（6 个会话）**：每个新会话的首次调用只命中 **1,408–2,816 tokens**，而 prompt 有 12K–22K；断点落在 `resources/scenes/*/prompt.md` 的 `当前工作目录：{{cwd}}` 行（台账 `skeleton=47/49/52`，是全文第一处结构性可变内容），其后的 pi-context 段（约 20K 字符）全部作废。

**「单轮 92.4%」= 该情形的上限，不是偏低**：该 16 步单轮会话的未命中 44,950 ≈ 全轮新增内容总量（零重复未命中），即算法在该情形下已无浪费。命中率的分母含每轮新增的消息，新会话/单轮会话天然偏低 —— 判断前缀有没有被破坏不能拿绝对读数跨会话比，只能看「变更轮 vs 无变化轮」的差（探针把它测成 62% → 93.2%）。

**禁止进系统提示词的最终纪律清单**：时间 / 记忆内容 / 个性化 / 工作区文件内容 / cwd。时间与 cwd 的唯一来源是 `session-host` 的 hidden context（`current_time` / `workspace_context`），记忆内容与个性化由 `prompt-switch` 的 `context` 事件每请求注入。**唯一留在提示词里的工作区文件内容**是 pi 的 `contextFiles`（AGENTS.md 类项目指令）：forced 整串替换让 pi 不再自动附加它，只能由 `formatPiContextBlock` 拼回 pi-context 段；pi 在会话建立时装载（`_baseSystemPromptOptions`）、会话内不重读，不属逐轮事实，故不破坏字节稳定 —— 列为受限例外。

**与 LOG13 / CACHE6 的关系**：LOG13（消息逐条稳定标识）与 CACHE6（命中前缀边界反推）已于 2026-09-17 落地（见下方小节）。现在除了探针读数与 `request_snapshot.systemSegments` 的间接判定，面板能直接说出「断在第几条消息 / 断在消息列表之前」，以及那条是新增还是内容变了。

**命中前缀边界反推（CACHE6）的前提与局限（2026-09-17）**

**怎么反推**：三层依据，一层是估算、两层是确定性的。
① **token 对齐**（估算）：把本轮请求的逐条消息 token 估算累加，与 `cacheRead` 对齐 —— 前 N 条命中、第 N+1 条起未命中。
② **逐条 diff**（确定性）：用消息 id + 内容指纹与上一轮逐条比对，定位首个差异位置；`appended`/`changed`/`moved` 由「这条在上一轮存不存在、内容变没变、位置变没变」三者分派。
③ **系统提示词分段 diff**（确定性，2026-09-17 补）：`request_snapshot.systemSegments` 每段带内容指纹（`SystemSegmentStat.fp`，与消息指纹同一算法 `contentFingerprint`），相邻两轮逐段比对 —— 断点判为 `before_messages` 时能指认到**哪一段**：内容变了（source + 两轮字符数）/ 新增 / 消失；逐段一致 → 断点在提示词**之前**（工具集 / 模型变了）；旧台账没有分段指纹或集合相同而顺序不同 → 如实返回不确定。指纹不可逆，仍不落正文。

**前提（都对不上时函数如实返回不确定，不编数）**：
- token 是**字符估算**（`estimateTokens`：CJK 约 1 token/字、其余约 4 字符/token），**不是真 tokenizer**；
- 消息**之前**那段固定前缀（系统提示词 + 工具定义）没有逐条 token 明细，只能拿**上一轮**的真实 prompt 总量（`billedInputTokens`）减去上一轮消息估算总量来**定标**。因此上一轮与这一轮的前缀不一致时（改两轴、换工具集、换模型），定标本身就偏；
- 于是边界带一个**消息条数量级**的误差。函数用确定性的那层收紧它：命中量不可能超过「与上一轮逐条相同的那段」，超出就收敛到差异位置并标 `uncertain`；断点那条与上一轮完全相同时也标 `uncertain`，不硬说它变了；
- `cacheRead <= 前缀估算` 时给 `before_messages`：断点在消息列表之前（系统提示词 / 工具定义变了，或缓存整体失效），**不指认某一消息**（改由 ③ 指认系统提示词的段）；
- 分段 diff 只覆盖系统提示词（**工具定义不在 `systemSegments` 里**）；分段逐段一致时只能如实说断点在提示词之前，不再往下猜；
- **瞬态注入项不算断点**：`prompt-switch` 的 `context` 事件每请求现算、不落会话的那条（`customType: "kamibuddy-runtime-context"`）在相邻两轮表现为「上一轮尾部有、这一轮换了一条」，归因前按 `MessageRef.transient` 标记剔除（旧台账退到「role 归 other 的尾部条目」这一可判定条件）—— 否则每轮都会误报一次；它是**有意设计**，不是故障；
- 相邻两轮的配对按**台账顺序**取（跨 run 也算：provider 比的是上一次请求），中间若有压缩，历史被整体替换，diff 会如实说「全变了」。

**还答不了什么**（别把它当账单用）：工具集变了导致的断点（工具定义不在分段清单里，只能确定「断在系统提示词之前」）；同一段内部改在哪儿（只到「这一段变了」，不到字符位置）；provider 侧的真实 token 数（要真 tokenizer 或 provider 的缓存细分）；`cacheWrite`（写侧）的边界；以及「同一轮 cacheRead 偏低是 TTL 到期还是被驱逐」—— 那是 CACHE3 的归因口径，反推不重复回答。

**代价**：`messageList` 每轮几十条、每条约 60 字节，与 LOG18 的日志体积问题同向 —— 它是有用数据，但改日志轮转时别忽略它。

## 优先级建议

排的是「交付价值 ÷ 成本」。**第一梯队的东西是一条链，拆开做没有意义。**

**第一梯队 · 把「一轮讲清楚」这件事做死**

1. **CTX6 + LOG13 + VIEW8 —— 三个必须一起做。**
   给每条消息一个稳定标识（LOG13），才能算出「这一轮比上一轮新增了什么」（CTX6），
   才有单轮完整入模上下文可下钻（VIEW8）。这是你原话里「模型当前完整上下文长什么样、
   经过一轮新增了什么」的直接答案，也是整个清单里唯一还缺的**结构性**能力。
   **进展**：LOG13 已于 2026-09-17 落地（`request_snapshot.messageList`）；
   CTX6（增量 diff 的展示）与 VIEW8（单轮完整上下文下钻）仍缺 —— 依赖已就位。
2. **CACHE6 —— 命中前缀边界。** 依赖 LOG13（同一个消息标识），所以跟着 1 走。
   技术上最硬（要重建 prompt 逐条 token 账本），但它把「命中率 63%」变成一个
   可解释的结论：「前 12 条消息命中，第 13 条工具结果变了，后面全废」。
   **这一项做完，这套观测就有了别家没有的东西。**
   **已落地（2026-09-17）**：`shared/cache-prefix.ts` 纯函数 + 任务诊断面板单步详情；
   口径是估算对齐，前提与局限见三、缓存 一节的 CACHE6 小节。

**第二梯队 · 成本与性能的基本功**

3. **CACHE5 + costBreakdown 分项** —— 数据都在了，纯渲染，一次做完。
   （`reasoning` 已于 2026-09-16 随任务诊断面板的单步详情落地，见 VIEW15。）
4. ~~**LOG14 / PERF6 tok/s**~~ —— ✅ 2026-09-15 落地，随会话指标条一起（见 VIEW14）。
5. **CTX5 autocompact buffer** —— 对齐 WorkBuddy `/context`，消除「为什么还不压缩」的困惑。
6. **PERF7 / CACHE7 趋势与分位** —— 从「当下值」升级到「看得出来变差」。

**第三梯队 · 长任务与多代理**

7. **AGG8 子代理台账 + AGG9 审批等待计时 + TOOL4 大输出外置** ——
   三件一起做：多代理并行时，「谁在等审批吃掉了两分钟」是真实的耗时段，
   而子代理的输出是上下文爆炸的主因。
8. **TOOL3 工具结果回溯 + OPS3 隐私分级** —— 把 TOOL_CONTENT 做成**默认关闭的开关**
   （照 WorkBuddy 的三级 opt-in），既满足取证需求，又不破坏「默认不记正文」的纪律。
9. **TOOL6 失败原因归类** —— 权限拒绝 / 超时 / 工具报错分开统计。

**第四梯队 · 交付与洞察**

10. **VIEW10 观测报告导出（HTML）** —— 对标 `/insights`，也是给同事演示的抓手。
11. **VIEW11 AI 使用洞察** —— 用自家 automation 调度器跑（同记忆蒸发的路子）。
12. **VIEW9 热力图 + OPS1 观测量自检**。

**明确不做（已决策，勿反复）**

OPS4 脱敏上传、OPS5 OTel 导出、OPS6 RUM/埋点/设备指纹——
理由分别是「无上传需求」「AGENTS.md YAGNI」「依赖腾讯内部能力」。

**LOG18 已移出本列**（2026-09-15）：原 YAGNI 理由「事件量小且采样是事后补丁」
被实测推翻（单日 5.3 万条 / 38 MB），改判为 ❌ 待办，见该行。
