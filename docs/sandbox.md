# 沙箱（Windows 受限令牌写约束）

> 状态：一期（OS 级写约束）2026-09-15；二期 P0（链接收敛 + 拒写可读 + 一次性提权）2026-09-16；三期（配置即代码写保护 + 安全名单）2026-09-16；四期（先跑后问 + read-only 沙箱接入）2026-09-16 —— 均已落地。
> 代码在 `src/sandbox/`（沙箱本体）、`src/daemon/sandbox-runner.ts`（策略层）、`src/core/path-containment.ts`（权限门侧归属判定）、`src/extensions/safe-commands.ts`（内置安全名单）；决策记录见 `ARCHITECTURE.md` §4.4b。
> 本文面向**第一次接触这块的人**：先讲清「为什么需要」，再讲「怎么做到的」，
> 最后是代码地图、设计理由、已知边界与开发规划。

## 是什么

一句话：**让「模型写不出工作区」成为操作系统保证的事实，而不是靠命令文本匹配去猜。**

一个具体例子（这就是一期的全部用户可感知价值）：

> 默认权限档下，模型执行 `powershell` 往桌面写文件。
> 你在审批弹窗里点了「**允许**」——文件**仍然写不进去**，命令返回「拒绝访问」。

在引入沙箱之前，点「允许」就等于放行；模型写的到底是不是你批准的那个位置，没人能保证。

## 为什么需要它

权限系统原本有两层，各有各的盲区：

| 层 | 它管什么 | 盲区 |
| --- | --- | --- |
| **权限门**（`permission-policy.ts`） | 要不要问用户 | 看得见 `write`/`edit` 的**目标路径**，但看不见 `powershell` 命令**内部**要写哪儿 |
| **危险命令检查器**（`command-guard.ts`） | 这条命令能不能跑 | 是**静态文本匹配**——它自己的文件头就写明：base64 重编码、变量拼接、写个脚本文件，三种都能绕过 |

于是剩下唯一的"防线"是：**每条 shell 命令都弹窗问用户**。但用户面对一长串 PowerShell，通常看不出它到底要往哪儿写。这是产品级的问题。

沙箱把这一层补上：**约束不再来自"我们猜这条命令想干什么"，而来自操作系统"这个进程能碰什么"。**

## 怎么做的（原理）

### 三个 Windows 机制，一句话各讲一遍

- **受限令牌（restricted token）**：每个进程都持有一张"身份证"（令牌）。我们复制自己的身份证，做一张**打了折的副本**，并在副本上附一份**白名单**（受限 SID 列表）。拿这张副本启动的进程，每次访问文件要通过**两道检查**：正常的权限检查，加上"白名单里有没有这一项"。
- **ACL 授权**：目录的"门禁名单"。我们给自己的目录加一条记录，允许白名单里的某个编号写入。
- **Job Object**：一个进程组。它的关键性质是「最后一个句柄关闭时，组内**所有**进程一起被杀」——超时清理时能连孙进程都收掉，不留孤儿。

### 拼起来

```
1. 复制自己的进程令牌
2. 派生受限令牌，白名单里放：
      登录 SID（系统要求，缺了进程会在 DLL 初始化阶段直接死掉）
    + Everyone（同上）
    + 每个工作区一个专属编号（capability SID，由工作区路径哈希而来）
3. 给工作区目录、以及该会话的私有 temp 目录的 ACL 加上那个专属编号的写权限
4. 用受限令牌启动 powershell.exe —— 它写工作区之外的地方时，
   第二道检查（白名单）过不去 → 操作系统直接拒绝
5. 进程挂进 Job Object → 超时能杀掉整棵树
```

**为什么不需要管理员权限、不需要建账号**：我们只对**自己拥有的**目录授权，而目录所有者天生就持有 `WRITE_DAC`（改门禁名单的权限）。这一点是 dsh 相对 codex 的关键简化，也是我们能在「给同事试用」这种场景里零摩擦落地的原因。

### 一次命令的完整生命周期

```
【会话建立】 探测（环境能不能用）+ 预热授权（给工作区/私有 temp 授写）
             ↑ 首次较慢（见下文数据），之后每次 1ms —— 所以放在建会话时，不放在命令时
【模型调用】 ① 无人值守闸：定时任务的后台会话一律拒绝 shell
            ② 危险命令检查器：五类危险命令直接拒绝（不执行）—— 名单放行的命令照样过
            ③ 权限门审批：要不要问人
                 ↑ 路径判定在这里**归一化真实路径**（junction 绕不过，决策 12）
                 ↑ 写「配置即代码」文件（.git/config、package.json、.pi/extensions/** …）
                   一律高风险询问，即使在工作区内（决策 15，WorkBuddy 同类层）
                 ↑ powershell 命令：唯一例外是配置文本闸，其余一律放行到执行层
                   （对齐 dsh —— 能不能跑由执行层沙箱决定，门不预判）
                 ↑ bash 维持高风险询问（无检查器、无法包沙箱，fail-closed）
            ④ 提权判定（仅当模型带了 sandbox_permissions）：
                 严格变宽？→ 有审批通道？→ 策略不是 never？→ 才问用户
                 任一不满足 = 拒，且命令**一行都不跑**（决策 14）
            ⑤ 沙箱执行：现场探测 → 派生受限令牌 → 跑命令（含私有 temp、Job）
                 ↑ 探测/授权/令牌/spawn 任一失败 → **拒绝执行**，绝不无约束重跑
                   （对齐 dsh SandboxUnavailableError，决策 16）
            ⑥ 结果回给模型：状态行 + 输出
                 + 看起来被写约束拒了：拒绝标记（+ 能提权时才给出路，决策 13）
```

【写工具（write/edit）走的是另一条路】它们在 daemon 进程内执行、**持完整令牌**，
沙箱管不到 —— 那条路上唯一的边界是 ③ 的权限门（所以决策 12 才要紧）。

## 关键设计决策（以及为什么）

每一条都有实测或事故支撑，改动前请先看理由。

### 1. 授权跑在 worker 里；预热时机 = 选定工作空间那一刻

实测授权开销随文件数**略超线性**增长：

| 工作区文件数 | 首次授权 | 幂等命中 |
| --- | --- | --- |
| 100 | 40 ms | 1 ms |
| 1000 | 477 ms | 1 ms |
| 5000 | **3134 ms** | 1 ms |
| 25020 | 5262 ms | 3 ms |
| **43723** | **19.3 s** | 1 ms |

那条 `SetNamedSecurityInfoW` 是**同步**的：Windows 在这一次调用里把继承 ACE 传播到整棵子树。2026-09-17 从事件日志定到的现场（`session:prompt` → `run_started` 的间隔）：

| 工作区 | 首条消息 → agent 起跑 |
| --- | --- |
| 空临时任务目录（45 / 94 / 154 / 423 ms 四次） | 最快 |
| 真实项目目录 AgentHub（43,723 条目） | **19,657 ms** |

第二条就是用户报的「发送后白好一会才动」：授权堵在 daemon 的**单线程**上，那 19.6 秒里它连「消息已收到」都发不出去（用户气泡由 daemon 确认后回显，不是 UI 乐观插入）。所以两条一起改：

- **授权搬进 `worker_thread`**（`src/daemon/sandbox-prepare-{protocol,worker,client}.ts`）：主线程只等 promise，同步 FFI 落在 worker 里。验收看 `scripts/probe-sandbox-worker.mts` —— 25,020 条目授权 5,262 ms 期间，主线程事件循环最大滞后只有 **10 ms**。这是三家唯一有一条现成范式的做法：codex 对**读根**的 ACL 就是这么做的（后台 helper + 单飞互斥），写根仍留在 spawn 路径上；dsh 与 WorkBuddy 都没有（dsh 把「首次全树传播」写进了 Known Limitations，WorkBuddy 换成了不落 ACL 的规则引擎）。
- **预热提前到「选定工作空间/目录」那一刻**（daemon 的 `applyWorkspace`），不等第一条消息 —— 用户从选目录到按下发送通常还要写一段话，够它跑完。会话建立时仍会兜一道（resume、启动默认目录等不经 applyWorkspace 的路径）。非 `workspace-write` 档位秒退（不留 ACE、不起线程）。

授权成本会随诊断上报：设置页权限区多一行「最近一次沙箱授权：哪个目录 / 首次还是幂等 / 耗时 / 目录条目数」，事件日志的 `sandbox_status` 也带上同一组数字（`prepare` 字段）。

### 2. ACE 常驻，不撤销

授权过一次就留着（幂等命中只要 1ms）。这样**只有「该工作区第一次运行」付钱**，之后每次开会话几乎零成本。代价见「已知边界」里的 ACE 残留一条。

### 3. 默认 DACL 的授权受托者必须是「身份内 SID」

**这是 2026-09-15 上线首测回归的根因**，务必别改回去：令牌的**默认 DACL**（决定子进程新建对象如匿名管道的权限）里，ACE 的受托者**不能是 capability SID**（`S-1-4-*`），否则在某些启动上下文里子进程直接死在 DLL 初始化（`0xC0000142`）——表现为**每一条命令都失败**。
判别矩阵证明：受限列表**含**外来 SID 无害、文件 ACE 用外来受托者无害、**唯独默认 DACL 用外来受托者必死**。所以：默认 DACL 恒用**登录 SID**（两档受限列表里都在），文件授权保留 per-workspace capability SID（隔离边界不变）。

### 4. 私有 temp 用「显式环境块」，不改本进程环境

子进程的 TMP/TEMP 指向自己的私有 temp 目录。**推翻了 dsh 的一条结论**：他们注明「显式传环境块会 `ERROR_INVALID_PARAMETER`」，因此改去修改**自己进程**的 TMP/TEMP 让子进程继承——那条路我们不能走（会污染整个 daemon，影响所有会话）。实测两次对照证明根因是漏了 `CREATE_UNICODE_ENVIRONMENT` 标志（`lpEnvironment` 默认按 ANSI 解释 UTF-16 块）。

### 5. piped 路径也要挂 Job Object

dsh 只给「继承 stdio」的路径配了 Job。我们的工具需要**捕获输出**（喂回模型），走的是管道；没有 Job 的话超时只能杀掉直接子进程，`powershell -Command "node x.js"` 里的 node 会变孤儿继续跑。

### 6. 等待必须异步轮询，不能阻塞

dsh 用 `WaitForSingleObject(INFINITE)` 同步等待——它跑在独立 runner 进程里无所谓；我们在 daemon（单线程 JS）里，阻塞 120 秒等于把所有会话连同界面事件一起冻住。

### 7. 档位映射：只有 `workspace-write` 进沙箱

| 权限档 | 进沙箱？ | 理由 |
| --- | --- | --- |
| 只读 | 不进 | 权限门已把 shell 全拒，走不到这里；真走到了也不该假装受限 |
| **默认（workspace-write）** | **进** | 一期主战场 |
| 允许完全访问 | **不进** | 该预设的文案写的是「不限制文件范围」，加了沙箱就是文案说谎 |

### 8. 沙箱不可用时**降级 + 明确说明**，但要翻转

探测失败时退回「今天的行为」（直接执行），并在**工具结果与设置页**写明「未受操作系统级写入约束」及原因。这不是 fail-open：今天本来就没有沙箱，降级等于「没有改善」，不等于「打开了一个洞」。
但**下一期放松审批时，这条判据必须翻转成 fail-closed**——放松的依据就是沙箱存在，所以那时探测不可用**不得放松**。

### 9. 「启动自检」只放在探测期（安全支点，别挪）

探测时用**我们自己选的**命令真跑一次，起不来就报不可用。
**为什么不能放在每条命令上**：退出码由子进��控制。若在命令执行后把「进程没起来」类退出码判定为沙箱故障并降级重跑，模型只要写
`Set-Content C:\outside\x.txt "data"; exit 3221225794`
就能伪造该信号 → 我们判定「沙箱坏了」→ **不受约束地重跑同一条命令** → 写成功。那是真实的沙箱逃逸。放在探测期则命令与哨兵值都由我们决定，模型无从伪造。

### 10. 不给子进程新建控制台

daemon 是 Electron `utilityProcess`（GUI 进程），**没有宿主控制台可继承**。不加 `CREATE_NO_WINDOW` 时，每个受限子进程都会新建一个控制台——用户看到的是「闪一下黑窗口」。

### 11. 子代理同等待遇（指沙箱本身；提权是例外，见决策 14）

子代理与主会话同 cwd、同权限设置。若只给主会话接沙箱，委派就成了绕过写约束的后门（而委派是模型可自主发起的）。

### 12. 权限门的归属判定必须解析链接（二阶段，2026-09-16）

**这是实测出来的缺口，不是理论加固。** `scripts/probe-junction-containment.ts` 在真实文件系统上跑出：

| 场景 | 加固前 | 加固后 |
| --- | --- | --- |
| 工作区内建 junction 指向区外，`write` 它 | **allow**（文件落到区外，且**不弹窗**） | ask |
| 工作区内建 junction 指向凭据目录，`read` 它 | **allow**（禁区被完全绕过） | deny |

原因：`isInside` 只做 `resolve()`，不解析符号链接。而 **junction 不需要管理员权限**就能创建（symlink 才需要），所以这是模型真走得通的路径。

写侧的 `write`/`edit` 走 pi 的 fs 工具、在 **daemon 进程内**执行（完整令牌），沙箱管不到 —— 权限门是那条路径上唯一的边界。

实现要点（`src/core/path-containment.ts`）：

- **归一化最深的存在祖先**，而不是直接 `realpathSync`：判定发生在写入之前，目标文件通常还不存在（write 新建是常态），直接 realpath 会 ENOENT。链接只可能在已存在的那一段里。
- **纯大小写差异一律丢弃，保留词法形式**。`realpathSync.native` 会改写成磁盘的规范大小写，而这个值同时流向 `details`（弹窗展示）、`writeBackPath` 与 `rememberKey` —— 让它随「祖先目录恰好存在与否」变形，会让同一目标在两次调用间得到不同的会话记忆键（用户批准过的目录第二次又被问）。Windows 的 `path.relative` 本就大小写不敏感，丢弃这一类不损强度。
- **`details` 也用归一化后的值**：若只归一化判定而把链接原样展示，弹窗就会**隐瞒文件的真实去处** —— 用户以为在批准「写工作区里的某个文件」，实际批准的是写区外。那比不归一化更糟，它把知情同意变成了误导。
- 顺带**消掉了一处重复**：`permission-rules.ts` 原本抄了一份 `isInside`，注释里写着「两处若将来要改语义必须一起改」——这次就是那个「将来」，于是把实现移到两侧都能 import 的 `core/`。

**边界要诚实**：我们是门、不是写入方，残留 TOCTOU 见已知边界 8。这条挡的是「模型误用 junction」与「随手的路径穿越」，**不是**内核边界。

### 13. 拒写识别必须用「与语言无关」的签名（二阶段）

让「被策略拒了」对模型可见，否则它只看到裸的报错，会反复改写命令（以为是自己写错了）。

但**照搬 dsh 的做法在这里行不通**，这是实测结论（`scripts/probe-denial-text.ts`，中文 Windows 11）：

PowerShell 按控制台代码页（中文机器 936/GBK）输出 stderr，而 `runSandboxed` 按 **UTF-8** 解码。于是本地化的「对路径…的访问被拒绝」到我们手里是**乱码**（`��·����…���ķ��ʱ��ܾ���`）。所以两条直觉做法都永不命中：dsh 的英文方言（`access is denied` 等）在中文机器上没有，改匹配中文文案则匹配的是乱码前的文本。

可靠信号是乱码里**活下来的 ASCII**：`UnauthorizedAccessException`（.NET 异常类型名）与 `PermissionDenied`（PowerShell 错误类别）。GBK 与 UTF-8 对 ASCII 字节一致，所以它们穿过编码错乱后原样可见。这比本地化文案更强：中文版、英文版、任何语言版都命中。dsh 的三条英文签名一并保留（英文版 Windows、node EACCES）。

**已知漏网**：cmd.exe 重定向失败给的是「文件名、目录名或卷标语法不正确」，一个 ASCII 标记都没有。影响很小（本层只跑 `powershell.exe`），且漏报只是少一句提示。

### 14. 一次性提权：只能变宽、只此一次、绝不自动（二阶段）

模型可以带 `sandbox_permissions` + `justification` 为**这一条命令**申请更宽的档位（字段名照 dsh 逐字）。判定住 `sandbox-runner`（策略层），顺序是**有序的 fail-closed**：

```
严格变宽？ → 有审批通道？ → 审批策略不是 never？ → 才问用户
```

顺序本身是语义：**不合法的申请不该惊动用户** —— 否则模型可以靠刷弹窗骚扰，直到对方随手点了允许。

四条纪律：

1. **两个安全支点**。stderr 由子进程控制，模型可以伪造「拒绝」文本；识别它**只追加一段文字**，永不自动放宽（真正的加宽必须用户点头）。这与决策 9 是同一条推理——谁让它自动降级重跑，就是在重造一期修掉的逃逸。
2. **批准到 `workspace-write` 时仍然进沙箱**。判据看提权**后的档位**，不是「有没有提权」——否则「批准到工作区可写」会变成「完全放开」，比用户批准的更宽。
3. **只对本次调用有效**。审批用 `risk: "high"`，而弹窗对高风险不提供「本次会话记住」、回程也忽略 `remember` —— 跳过沙箱是我们能给的最宽授权，不该有任何免检。
4. **子代理不接这条通道**（有意偏离「决策 11 同等待遇」）。不接 = 子代理**不能**放宽约束，那是 fail-closed；反过来接上才需要论证——委派是模型可自主发起的，让它在委派里申请「跳过沙箱」等于把高风险授权挪到用户更难判断的位置（弹窗里只有子代理的命令，没有委派的来龙去脉）。真需要提权的活儿留在主会话做。

**过渡态的代价**：一条提权命令现在会弹两次（权限门的 shell 审批 + 提权审批）。这正是下一期要消掉的那一半。

### 15. 审批放松：先补「配置即代码」写保护，再用两层名单（三期，2026-09-16）

三期原本只是一个「内置安全前缀名单」。**实现前的探针把它推翻了一半**，于是变成了两件事：

**第一件（前提修复）：「配置即代码」文件的写保护。**

`scripts/probe-config-write-exec.ts` 实测（git 2.55.0）：工作区内的写入免审批，于是模型可以**静默**写下这批内容会变成被执行行为的文件：

- `.git/config` → `core.fsmonitor` 让 **`git status` 与 `git diff` 执行任意命令**；`[alias] st = !…` 同理（内建名不可被 alias 劫持，自定义名可以；`core.pager` 在 stdout 非 TTY 时不触发——我们捕获输出，这条恰好无效）
- `.pi/extensions/*.ts` → pi 从工作目录加载项目级扩展，**会话建立时加载即以本进程权限执行**，权限门在它之后根本拦不到（project-trust.ts 称之为「唯一在工具层之前的攻击面」）
- `.git/hooks/*` → **用户自己**下次提交时执行（逃出我们进程的持久化）
- `package.json` / `.npmrc` / `.github/workflows/*` 等

结论：**命令的行为不由它的名字决定，而由工作区里一个可被改写的文件决定**。任何基于命令名的白名单，前提都是这批文件的写入需要审批。所以先把它们加进高风险询问（`isConfigAsCodePath`，判据：**内容会被自动执行，且没有任何命令点名它** —— `evil.ps1` 不在名单里，`powershell ./evil.ps1` 点了名、由 shell 审批把关；`git status` 不点 `.git/config` 的名），再做名单。

名单的**精度**与宽度同样重要：pi 只加载 `.agents/skills`，本仓库的 `.agents/notes/` 全是文档 —— 把它一并拦下不是「多点一次弹窗」，而是训练用户对高风险弹窗条件反射点允许，那正是 project-trust.ts 警告过的失效模式。

**第二件：两层名单（`safe-commands.ts`）。**

- **第一层（无条件放行）**：只读自省类 —— `git status/diff/log/show/rev-parse`、各类 `--version`、`pwd`。它们不写文件、不跑项目自己的代码，沙箱在不在都一样安全。
- **第二层（沙箱确实生效才放行）**：构建类 —— `npm run`、`npm test`、`npx tsc`、`tsc`。它们执行 package.json 的脚本 = 任意代码执行，写侧靠 OS 写约束兜住。

名单前的**三道结构闸门**（先于前缀匹配，顺序不能反）：单段（`splitCommand`）、无管道/重定向/子表达式/调用运算符、无可执行体注入旗标（`-c`、`--ext-diff`、`--exec`、`--output`、`-e`、`--node-options`…）。闸门 2 存在的直接理由：`splitCommand` **刻意不切单个 `|`**，于是 `git status | node -e "…"` 整体以 `git status` 开头，前缀匹配与危险命令检查器都拦不住 —— 这是真实的注入面。

**有意排除**（都写进了测试，防止将来被「顺手」加回去）：`git branch`（`-D` 是写操作，前缀分不出来）、`npm install` / `npm ci`（执行依赖包的 install 脚本 = 供应链入口）、bash（没有危险命令检查器，不放松）。

**判据读 readiness 而非「探测可用」**：`probeSandbox` 通过不代表沙箱能用 —— `prepareSandbox`（ACL 授权）是独立失败路径，失败后执行层会降级成无约束执行。若门只看探测，就存在「免审批放行 → 授权失败 → 无约束执行且没人批准过」。解法：判据读 `SandboxDiagnostics`（`warmUpSandbox` = probe + prepare，只有两步都成才报 `available: true`），且 **按工作区问**（`isSandboxReadyFor(cwd)`）、**未知一律当不可用**（预热是异步的，门可能早于它完成 —— 那时继续问，自愈）。这与一期「探测失败就降级执行」是**相反**的判据方向，正是 spec 反复预告的那次翻转。

**两条不变的纪律**：用户写的 deny 规则赢过内置名单（最严获胜）；危险命令检查器照旧独立运行（名单只影响「要不要问」，不影响「能不能跑」）。

**残留风险（如实写）**：若工作区里**本来就有**恶意 `.git/config`（克隆了敌对仓库），`git status` 仍会执行它 —— 与我们放不放松审批无关，VS Code / JetBrains / 任何 git GUI 打开目录时都会自动跑。那种情况下我们不是有意义的边界。另外「配置即代码」是开放集合（各种 `*.config.js`、编辑器约定…），名单覆盖已知高价值项、**不声称穷尽**。

### 16. 先跑后问：闭环「门放行 ⟹ 执行必受约束」（四期，2026-09-16）

对齐 codex/dsh/WorkBuddy 的结论（见对比表）：体验差距的本体是**默认方向** —— 它们 workspace-write 下命令直接进沙箱跑、被拦才问；我们事前逐次审批。四期按方案 A（折中对齐）翻转：

```
凭据拒 → 规则 → 名单 → 配置文本闸弹窗 → 沙箱就绪直接跑（OS 兜）→ 未就绪弹窗
```

**这个翻转成立的前提是一条闭环不变式：门放行的命令绝不能落到无约束执行。** 三段保证：

1. 门读 readiness（三期已建，蕴含 probe + ACL 授权都成功），未知一律弹窗；
2. **runner 装配失败按 readiness 分流**（本期新增）：就绪会话 fail-closed 拒绝（dsh `SANDBOX_UNAVAILABLE` 同款语义）——否则「没人看过的命令」会被降级成无约束执行；未就绪会话维持一期降级纪律（那些会话的门在逐次弹窗，有人工终审）；
3. **read-only 档的 runner 分支翻转**（本期新增，安全关键）：旧代码 `mode !== workspace-write → fallback` 对 read-only 意味着「无沙箱全权限跑」，此前靠门全拒 shell 掩盖着（防御性死代码）。门放行只读沙箱执行后，read-only 必须进沙箱（受限列表无任何写能力），仅 danger-full-access 保持 fallback。read-only 档由此获得可用 shell（dsh 同语义：命令能跑、文件动不了，连 `.git/config` 都写不进 —— fsmonitor 链在 OS 层就断了）。

**放行的完整前提（缺一不可）**：名单外、不碰配置路径（文本闸）、沙箱就绪。

**对齐 dsh 的最终形态（四期收尾，用户指示「已实现的，标准要向他们对齐」）**：

门对 powershell 命令**不再审批**——一律放行到执行层，唯一例外是配置文本闸（WorkBuddy「受保护文件全模式拦」的同类层）。执行层现场 confine（dsh 同构：能力是执行时事实，预热只是性能优化与诊断），**任何一环失败（探测/授权/令牌/spawn）一律拒绝执行**，绝不无约束重跑——dsh `SandboxUnavailableError` 的完整语义，官方出路同为「切 danger-full-access」。为此退役了三层自创物：

1. **名单层**（always/sandboxed 两层前缀名单 + 结构闸门的门侧使用）——dsh 没有名单，命令全部由沙箱兜；名单管「未就绪时谁免问」的场景随 fail-closed 消失（未就绪=现场探测还没做，做了就知道了）。名单文件退役，测试同步删除。
2. **readiness 判据链**（isSandboxReadyFor → gate → runner 的传递）——门不再判沙箱能不能用，runner 现场探测。全局 readiness 只剩设置页诊断用途。
3. **降级纪律**（一期遗留的「探测失败→无约束跑+说明」）——与 dsh 的 fail-closed 直接冲突，删除。

区外读询问同步撤除（read 家族区外放行，二次翻转 2026-09-09 事故条目，理由与理由链见 permission-policy.ts 阶段 2 注释）。

**同水位的已知代价**（codex/dsh 完全一致，如实写）：注入旗标/管道右端的任意代码免审批跑，可在沙箱内读密钥+外发（读/网无 OS 约束）。**保留的超出层只剩一层**：配置即代码保护（写侧 + 命令文本侧）——WorkBuddy「受保护文件全模式拦」的同类，用户认可。

## 与 codex / dsh 的对比

| 维度 | codex | dsh | 我们（二期 P0 后） |
| --- | --- | --- | --- |
| 实现 | Rust，约 67 个文件 | 纯 TS + koffi（MIT） | **纯 TS + koffi（移植 dsh）** |
| 运行身份 | 专用沙箱账号（离线/在线）+ DPAPI 存密码 | 只复制调用方自己的令牌 | 同 dsh |
| 安装成本 | 需一次性**管理员安装** | **零安装** | 零安装 |
| 写隔离 | 受限令牌 + ACL | 同 | 同 |
| 读隔离 | **有**（deny-read ACL） | 无（明确声明不支持） | 无（如实报 `partial`） |
| 禁网 | **有**（防火墙 + WFP + 本地代理 + 凭据代理） | 无 | 不做（见取舍理由） |
| 桌面处理 | 自建私有桌面 `CreateDesktopW` | 依赖共享宿主控制台 | 用户桌面 + `CREATE_NO_WINDOW` |
| 卸载 | **没有卸载路径** | — | 无残留账号/组，只留目录 ACE |
| 拒绝可读 | — | `denialSignatures`（英文方言） | **与语言无关的 ASCII 签名**（决策 13：中文机器上 dsh 那套永不命中） |
| 一次性提权 | 沙箱失败后自动无沙箱重试 | `approveEscalation`（模式阶梯 + 审批） | 同 dsh 的模式阶梯；**不学 codex 的自动重试** |
| 门侧路径判定 | — | `fs-sandbox`：写入前 realpath 再判包含 | **同向**（决策 12）：全链路归一化（含凭据禁区与读侧） |
| 每会话隔离 | — | 每会话独立 temp + 独立 SID，temp 授权可撤销 | temp 按**工作区**派生、不撤销（粒度粗一档，已登记待评估 4） |
| 额外 | 大量网络策略 | — | 启动自检、判别矩阵、真实进程冒烟、两个可复跑探针 |

**取舍理由**：

- **学 dsh**：零安装、纯 TS 可移植、只复制自己的令牌（不需要 UAC）。
- **不学 codex 的提权档**：它只多出「读隔离 + 网络隔离」，**写隔离的强度与一期完全等强**；代价是 UAC、常驻两个账号与一个组、**EDR/AV 高敏感**（建账号 + 改 ACL + 改防火墙是教科书级恶意软件特征）、可被企业组策略直接封死，且 codex 连卸载路径都没写。
- **不照抄 dsh 的 runner 层**：那层 argv 包装（`--workspace … -- <argv>`，失败退 127）是为「包任意 CLI 命令」设计的；我们在 daemon 进程内直接 spawn，用不上。同时补了它缺的三样：异步等待、piped 路径的 Job、显式环境块。

## 已知边界（必须知道它**防不住**什么）

不写清就会变成「假边界」——比没有沙箱更危险，因为人会以为有保护。

1. **读完全不受约束**。`WRITE_RESTRICTED` 机制上只管写。所以「读走密钥」这条路**仍只有危险命令检查器拦得住**——不得因为「有沙箱了」而削弱检查器。
2. **网络完全不受约束**。程序照样能联网外发。
3. **Everyone 可写的外部目录仍可写**。codex 专门做了「人人可写目录扫描告警」，我们还没做。
4. **NTFS 硬链接是文件对象别名**：工作区 ACE 会渗到工作区外的同一文件对象。
5. **FAT/exFAT 卷没有 ACL**：授权会「成功」但毫无效果 → 探测阶段直接报「不支持的文件系统」，界面不假装生效。
6. **ACE 残留**：工作区上会留下用户无法干净移除的授权记录（`icacls /remove` 会报 `ERROR_NONE_MAPPED`）。工作区是我们自己建的 `~/KamiBuddy`，可接受；而且它同时是性能设计的一部分（见决策 2）。
7. **管理员用户基本不受约束** —— 这是 Windows 安全模型的边界，不是 bug。**已实测**：提权运行时 Node 的 `writeFileSync` 能直接写进 `C:\Windows\System32`。
8. **权限门侧的链接判定有残留 TOCTOU**（二阶段新增，见下）。权限门在判定与 pi 真正写入之间存在时间窗口，攻击者可在其间换掉 junction。dsh 的 fs-sandbox 也只能靠「紧贴写入前重新归一化」收窄，并明确声明自己是 containment 而非 security boundary；我们的窗口更宽（判定在扩展里，写入在 pi 内部）。**写侧真正的内核边界仍然只有沙箱本身。**
9. **中文 Windows 上 PowerShell 的 stderr 是乱码**（既有问题，与沙箱无关，两条执行路径都有）：PowerShell 按控制台代码页（936/GBK）输出，我们按 UTF-8 解码。后果是模型看不懂自己命令的报错，削弱它自我纠正的能力。二阶段的拒写识别绕过了这个问题（用 ASCII 签名，见下），但**问题本身仍在**，值得单独处理。
10. **工作区里本来就有恶意 `.git/config` 时，名单内的 git 命令仍会执行它**（三期新增，见决策 15）：这与审批放松无关 —— 任何 git 客户端打开目录都会自动跑 `git status`。另外「配置即代码」名单**不完备**（开放集合），它是纵深防御的一层，不是可以依赖的边界。

因此强制力**恒为 `partial`**，界面如实说明，不因为沙箱生效就改成 `full`。

## 怎么验证

按「离真实运行环境有多近」分三层，各回答不同问题：

| 方式 | 命令 | 回答什么问题 |
| --- | --- | --- |
| 纯函数单测 | `npm test` | 引号规则、SID 派生、环境块、失败文案……不需要特权，任何平台可跑 |
| 集成测试 | `npm test`（Windows 上跑） | 真派令牌 + 真授权 + 真 spawn：区内可写、**区外被拒**、超时杀树 |
| **真实进程冒烟** | `npm run smoke:sandbox` | **在 Electron utilityProcess 里**（= daemon 的真实形态）跑 10 项断言，其中一项是**授权 worker**（把这个新入口 + koffi 在 worker_thread 里的加载放在生产进程类型下验证）。授权 worker 那条要求先 `npm run build`（它是独立构建产物；没构建过会打印一行「跳过」而不是静默通过） |
| 判别矩阵 | `npm run smoke:sandbox -- --diagnose` | 沙箱在某台机器上异常时，二分定位。可复跑 |
| **链接穿越探针** | `npx tsx scripts/probe-junction-containment.ts` | 权限门的归属判定能不能被 junction 绕过。**改动前 3×GAP，改动后 3×CLOSED** —— 既是缺口证据也是修复验收（含对照组，防布景搭错给出假结论） |
| 拒写文本探针 | `npx tsx scripts/probe-denial-text.ts` | 受限令牌拒写时 stderr 的**真实**文本（决策 13 签名表的唯一依据；换机器/换语言版 Windows 时复跑） |
| 首响延迟 | `npx tsx scripts/probe-first-response.mts` | 真实模型请求的「第一条 → 首 token」耗时与重试次数 |
| **授权 worker** | `npx tsx scripts/probe-sandbox-worker.mts [文件数]` | 授权搬进 worker 之后：主线程事件循环在授权期间**没有被打断**（25,020 条目 / 5,262 ms 授权 / 最大滞后 10 ms）、首次真传播、幂等命中仍生效。需先 `npm run build`（worker 是独立产物） |

**探针与测试的分工**：探针回答「这个缺口/事实存在吗」，跑在真实文件系统与真实沙箱上、可复跑；测试回答「它有没有回退」。两者都要有 —— 链接穿越的护栏同时进了 `permission-policy.test.ts`（`describe("链接穿越")`，真建 junction），因为探针是脚本、不进 `npm test`，接线若被改回纯词法判定不会有任何测试报警。

**为什么必须有「真实进程冒烟」这一层**：终端里跑测试是**有控制台**的进程，daemon 是**无控制台**的 GUI 进程，两者在受限令牌下的行为可能不同——上线首测那次回归正是因为终端测试全绿、应用里每条命令都失败。

## 开发规划

### 一期：写约束（已完成，2026-09-15）

- 受限令牌 + capability SID 写约束，接入 `powershell`（含子代理）
- 档位映射、启动自检、降级与诚实上报
- 工具链（冒烟 + 判别矩阵）、文档、变更提案

### 二期 P0：补沙箱管不到的两条（已完成，2026-09-16）

对比 codex 与 dsh 后发现的两个缺口都不在沙箱内部，而在它的**外面**：

1. **权限门的链接穿越**（决策 12）。`write`/`edit` 在 daemon 进程内执行、沙箱管不到，而唯一的边界只做词法判定 —— 实测可被 junction 绕过（连凭据禁区一起绕）。已加真实路径归一化，探针从 3×GAP 翻成 3×CLOSED。
2. **拒写对模型不可见、且没有正规出路**（决策 13、14）。已加与语言无关的拒写识别 + 一次性提权审批（`canEscalate` 与 `WIDER_MODES` 从此不再是死代码 —— 它们此前只有定义和测试，零调用点）。

这一期**不改善交互体验**（提权命令反而多一次弹窗），它是下一期的前置条件：放松审批的前提是「被拒时模型看得懂、且有正规通道」，否则模型撞墙后只会原样重试。

### 三期：配置即代码写保护 + 审批放松（已完成，2026-09-16）

原计划只是一个「内置安全前缀名单」。实现前的探针（`scripts/probe-config-write-exec.ts`）把前提推翻了：`git status` 会执行工作区内可被静默改写的 `.git/config`（`core.fsmonitor`，实测），`.pi/extensions/*.ts` 更是**会话建立时加载即执行**。所以三期实际交付了两件事（决策 15）：

1. **「配置即代码」文件写保护**：`.git/**`、`.pi/**`、`package.json`、`.npmrc`、`.envrc`、`Makefile`、`.github/**`、`.vscode/**`、`node_modules/.bin/**` 等一律高风险询问（即使在工作区内）。这同时修掉了一个**与放松无关的既有漏洞**（免审批写 git hooks = 逃出我们进程的持久化）。
2. **两层安全名单**：只读自省类（`git status` 等）无条件放行；构建类（`npm run` 等）仅在沙箱确实生效（probe + ACL 授权都成功，按工作区问）时放行，未知一律继续问 —— 那次预告的 **fail-closed 翻转**在这里兑现。

用户可感知的变化：默认档下 `git status`、`npm run build` 这类命令不再弹窗（沙箱可用的机器上）；改 `package.json` 会多一次高风险弹窗（低频，且它防的是真实的持久化攻击）。

### 四期：先跑后问 + read-only 沙箱接入（已完成，2026-09-16）

方案 A（折中对齐 dsh）：名单外命令在沙箱就绪时直接进沙箱跑，不再逐次弹窗；配置即代码文本闸保留（dsh 没有的防线）；read-only 档获得可用 shell（只读沙箱）；runner 装配失败按 readiness 分流（闭环不变式，见决策 16）。用户可感知的变化：**默认档下绝大多数命令不再弹窗**（与 dsh/codex 同级体验），弹窗只剩凭据/配置路径命中、用户 deny 规则、沙箱未就绪兜底三类。

### 五期候选（待评估）

- **命令语义解析**（tree-sitter PowerShell，codex 同款）：文本闸的残余缺口（拆散拼接）的彻底解法，也是写类命令精细化放行的基础
- **PowerShell 输出编码**（已知边界 9）：中文 Windows 上模型看到的报错全是乱码。影响每一条命令，是独立于沙箱的体验修复
- **人人可写目录告警**：缓解边界 3（codex 有，dsh 明确缺）
- **收敛 `docx_convert` / MCP stdio 到沙箱**：前者命令受控（收益小），后者需要把写根做成可配置（复杂度上一档）
- **每会话独立 temp + 互斥断言**：dsh 给每个会话独立 temp 与独立 SID；我们的 temp 按工作区派生（会话间共享）、从不撤销。隔离粒度粗一档。
- **读隔离 / 禁网**：只有走提权档（专用账号）才有意义，成本见「取舍理由」

### 明确不做

- **提权那一档**（专用账号 + 禁读 + 禁网）：写隔离强度与一期相同，代价是 UAC、常驻账号、EDR 敏感、GPO 可封
- 照抄 codex 的「沙箱失败后自动无沙箱重试」：太危险，一期选「拒绝 → 告诉模型 → 由模型显式请求提权」

## 踩过的坑（给后来人）

按「代价从大到小」排：

1. **上线首测回归**：受限令牌下每条命令都死（`0xC0000142`）。根因见决策 3。教训：判别矩阵要一次只变一个维度，且**必须在能复现的环境里跑**。
2. **在不等于目标环境的上下文里验证**：终端（有控制台）≠ utilityProcess（无控制台）。最早那次 spike 因此得出「私有桌面不需要」的乐观结论，而真相更复杂。
3. **手写精简版复现**：为"收敛变量"手写令牌派生，**漏掉了默认 DACL 那一步**，导致两组对照都失败、差点误判根因。**验证必须跑真实代码路径。**
4. **lpDesktop 的误导性**：codex 记录它会导致同一失败码，但我们四组对照（两档 × 设/不设）全部通过——它不是我们的根因。别把「上游的已知问题」当成「我们的根因」，要用对照证明。
5. **归因偏移**：统计脚本把「失败的尝试」当成独立的「第一条」，于是得出「无重试」的错误结论。分析日志时先确认事件序列的形状。
6. **外部环境也会伪装成我们的 bug**：那次「首条消息慢 30 秒」最终定位为 Windows DNS 后缀解析（网卡残留 `openstacklocal` 后缀 → `.local` 走多播超时），**与沙箱无关**。排查手法值得复用：写一个不碰自己代码的复现脚本，先证明问题是否存在于我们的边界之内。

以下是二期 P0（2026-09-16）新踩的：

7. **探针的前提可能不成立，而它不会告诉你**。为取拒写文本，第一版探针去写 `C:\Windows\System32`，假设「非提权用户必被拒」——结果 Node 的 `writeFileSync` **写成功了**（会话是提权运行的），三条探测全部无效，还在系统目录留下了文件。教训：探针要**断言自己的前提**（那条「意外写成功了」的提示就是补上的），而且要取「受限令牌拒写」的文本就必须真的走沙箱 —— 受限令牌与提权状态无关，那才是可靠布景。
8. **清理动作也要验证，否则会给出假的安心**。上一条的善后命令打印了三行「absent」，我差点就此收工 —— 但那是 bash 把路径里的反斜杠吃掉了（`C:\Windows\...` 变成 `C:WindowsSystem32...`），它检查的是不存在的相对路径。改用正斜杠重查，文件**真的在那儿**。教训：写死路径过 shell 时用正斜杠，且清理结果要看「REMOVED」而不是「absent」。
9. **别照抄上游的数据表，先在本机量一遍**。dsh 的拒绝方言是纯英文的，直接搬过来在中文 Windows 上**永不命中**（PowerShell 按 GBK 输出、我们按 UTF-8 解码，本地化文案到手里是乱码）。可靠信号反而是乱码里活下来的 ASCII 异常类型名。上游的**机制**可以学，它的**本地化数据**必须自己测（决策 13）。
10. **别拿被测对象给自己搭测试台**。验证「纯大小写差异要保留词法形式」时用了 `os.tmpdir()` 小写化当输入 —— 但它返回的是 8.3 短名（`WANGZH~1`），差异不只是大小写，于是那条用例测的根本不是它声称的规则。改用 `realpathSync.native` 搭布景才对。
11. **凭直觉写的断言会把错误固化成「正确行为」**。「指向区外的链接自身算不算工作区内」第一版写的是 `true`（理由：它确实是工作区目录列表里的一个条目）。但判定要回答的不是「列表里有什么」，而是**效果落在哪** —— 任何工具作用于它，读写都发生在区外，所以是 `false`。
12. **空的记录器不等于「没被调用」**。「伪造 stderr 不导致自动放宽」那条用例里 `sandboxCalls` 是空的，看着像「沙箱没被调用」，实际是我覆盖了假件的 `run`、而记账在**默认**实现里。断言执行次数就要由实际执行的那个假件来数。
13. **自己的计划也要复核推理方向**。计划里写着「子代理必须同等接线，否则委派就是绕过提权审批的后门」—— 这条是**反的**：不接线意味着子代理**不能**提权，那是 fail-closed，不存在后门（决策 14 第 4 条）。批准过的计划不等于正确的计划，实现时撞上矛盾要停下来重新推，而不是照着执行。

三期（2026-09-16）新增：

14. **白名单类安全设计的前提必须探针验证，不能靠直觉**。三期计划把 `git status` 列进「无条件放行」，理由写的是「不跑用户代码」—— 实现前随手一探（`probe-config-write-exec.ts`）就推翻了：`core.fsmonitor` 让它执行任意命令，`.pi/extensions/*.ts` 甚至加载即执行。直觉上「只读」的命令，行为可以由工作区里一个可改写的文件决定。若直接实现，交付的就是一条零审批的任意代码执行路径。
15. **写「与 X 无关」的注释前，先列出这个事实到底依赖什么**。两个缓存 bug 同根：`probeSandbox` 的探测结论与 `sandboxDiagnostics` 都被存成进程级单值，注释都写着「这台机器能不能用与会话无关」—— 但可用性其实依赖**工作区所在卷的文件系统**与**该目录的 ACL 授权结果**。今天只是显示不准，三期拿它当放松判据时就是安全洞。
16. **给判定链加放行通道时，先 grep 仓库里谁拿这些命令当「普通样本」**。三期名单让 `git status`/`git log`/`git diff` 变成放行，波及 4 个既有测试：两个失败（它们期望询问），两个更糟 —— **错误理由通过**（期望「规则放行」，实际名单放行，测试绿着但什么都没测到）。后者比失败危险得多，因为没有任何信号。修法是换成名单外的同前缀命令，并在注释里写明为什么换、为什么别换回去。
