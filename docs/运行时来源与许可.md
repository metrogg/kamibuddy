## 1. 结论（三项，各一行）

| 运行时 | 来源 | 校验 | 许可 | 体积（实测，2026-09-17） |
|---|---|---|---|---|
| `node` | nodejs.org 官方发行版 `node-v22.23.2-win-x64.zip`（`/dist/latest-v22.x/`） | 同目录官方 **`SHASUMS256.txt`**（含 win-x64.zip 与 `win-x64/node.exe` 两条 sha256） | **MIT**（Node 本体；同文件另含 V8/ICU/OpenSSL 等第三方段） | zip ≈36 MB；`node.exe` 87 MB |

| `python` | 沿用 uv：`uv.exe`（`scripts/fetch-uv.mjs`，钉 0.12.15）+ uv 从 `python-build-standalone` 拉 CPython | **sha256**（uv 元数据逐条带 sha256；GitHub asset `digest` 一致） | **PSF License Agreement**（CPython 本体）；uv 自身 MIT | uv.exe zip 17,578,593 B；Python stripped ≈22 MB |

## 2. 三个关键事实（本阶段查出来的、会改变后续做法的）

1. **MinGit 不含 `bash.exe`** —— 官方 MinGit 页明说它是 "intentionally minimal, **non-interactive**"
   分发，排除 Git GUI 与 **Git Bash**；shell 只以 `/bin/sh` 形式存在，"there is no `/usr/bin/bash`，
   and therefore scripts starting with `#!/usr/bin/bash` do not work"。busybox 变体的 shell 是
   busybox 的 `ash`（非 bash），且官方把 busybox 变体标为 **experimental**、不支持交互式终端。
   → **`gitbash` 运行时只能落在 PortableGit 上**（完整 Git for Windows）。
   spec/tasks 里"PortableGit / MinGit"并列的写法应收敛为 PortableGit（spec 文字由统一勾改处理）。
2. **PortableGit 是 `.7z.exe`（自解压 7z）**，仓库现有 `jszip` 解不了 7z —— 阶段 2 要补一个
   解包手段（建议构建期用 7-Zip/`7zr`，**只作构建期工具、不进产物**，以回避其 LGPL + unRAR 限制）。
   **状态更新（2026-09-18，见 §6）**：解包手段最终收敛为**运行期调发行物自带的 SFX 解包器**
   （`<artifact> -y -o<dir>`），7-Zip 依旧不进产物。
3. **`uv` 不做自己的 Python 发行版**：它按内置元数据从 `astral-sh/python-build-standalone`
   的 GitHub Release 拉（我们已实测其元数据文件里 windows/3.12.14 的 URL + sha256）。
   所以"沿用 uv 路线"与"直取 CPython 官方产物"并不是同一层选择：uv 路线 = uv 管理 +
   python-build-standalone 产物。

## 3. `gitbash` 的合规判定：**能合规**（含义务清单）

上游原文（Git for Windows FAQ "Licenses" 节，转载自其 release notes）：

> Git is an Open Source project covered by the **GNU General Public License version 2**（部分组件为
> GPLv2 兼容的其它许可）… This package contains software from a number of other projects including
> **Bash, zlib, curl, tcl/tk, perl, MSYS2** and a number of libraries and utilities from the GNU
> project, **licensed under the GNU General Public License**. Likewise, it contains Perl which is
> dual licensed under the GNU General Public License and the Artistic License.

**判定：我们这种"分发"场景（原先随包；2026-09-18 起改为按需联网下载，见 §6）能合规，
spec 无需因此回头改。** 但以下义务必须履行，
否则就变成不合规 —— 这些是**分发的前提条件**，不是"以后再说"：

| # | 义务 | 依据 | 我们怎么做 |
|---|---|---|---|
| 1 | 附许可文本 + 版权声明 | GPLv2 §1（"发布适当的版权声明和免责声明"） | PortableGit 解包后**自带**这些文件 → 不得删；产品内「关于 / 开源许可」页可读；安装/解包时随整树带入实例根 |
| 2 | 提供 Corresponding Source 的获取方式 | GPLv2 §3 / GPLv3 §6 | 三选一：随附源码 / ≥3 年书面要约 / 版本钉死的上游点对点下载指引（`git-for-windows/git`、`build-extra`、MSYS2 包仓库、bash、busybox…） |
| 3 | 不得附加额外限制 | GPLv2 §6 / GPLv3 §10 | 不对包内 GPL 程序加限制或额外许可门槛；不做 DRM / Tivoization |
| 4 | 保留版权与许可信息 | GPLv2 §1 | 原样分发（我们不改其文件，故无需标注修改），但不得剥离 LICENSE |
| 5 | 保持"独立程序"边界 | GPLv2 §2 末段 / GPLv3 §5（mere aggregation） | 只以**独立进程**调用（不进我们的地址空间、不静态/动态链接），KamiBuddy 本体才能保持闭源 |
| 6 | 商标用法 | Git 商标政策（**未逐条核对**） | 不在 UI/宣传位用 "Git" 名称与 logo 当我们的品牌，只在许可清单/致谢出现 |

**未确认（不阻塞阶段 0，但阻塞"正式上线"）**：逐组件（每个 `.exe` / `.dll`）的精确许可清单 ——
上游没有集中汇总，只能解包后收齐各 `LICENSE` 文件；本阶段**未下载/未解包**任何运行时，故未收。
按 `AGENTS.md §6`，内部使用阶段的风险置换由专人负责，本记录只把义务写清、不留空白。

## 否决方案

1. **否决：复用用户机器上已装的 Git / Python / Node。**
   理由：① 与既有口径直接冲突 —— `AGENTS.md §2`「不要求用户预装」与 spec 的 MODIFIED Requirement
   都以"用户什么都不用装"为前提；② **确定性**：版本不可控（Python 要 3.12 且要 `--only-binary=:all:`
   能取到 wheel；Node 要 ≥22.19（`package.json` 的 `engines`）；Windows 上压根没有自带 Git），
   环境随人而变；③ **失败不可归因**：诊断报告无法给出"缺了哪个版本"的唯一答案，违反 `§7` 的
   "响亮失败"；④ **安全面**：同名可执行文件在用户 PATH 上不可信，注入后我们要为它背书。
   例外（保留）：`HTML_TO_DOCX_VENV` 是**用户显式指定**的覆盖口，与"自动复用系统已装"是两回事。
2. **否决：复用 Electron 内置的 Node。**
   技术理由：① **形态不对**：Electron 交付的是单个 `electron.exe`，不是 `node.exe`；
   `ELECTRON_RUN_AS_NODE=1` 能当 Node 跑，但我们要注入 PATH 的是"一个叫 node 的 CLI"，
   用它就得包一层包装器，且每次调用起的是**整个 Electron 进程**（启动与 RSS 成本远高于 node）；
   ② **版本被绑死**：内置 Node 版本随 Electron 走（我们锁 `electron@44.2.0`），为了安全升 Electron
   会**静默**换掉模型脚本可用的 Node 版本/行为 —— 与托管运行时的"版本可寻址、可回滚"直接冲突；
   ③ **不是完整发行版**：不带 `npm` / `npx`（我们的脚本与模型习惯依赖 `npm` 与 `.bin` shim），
   且 `NODE_MODULE_VERSION`（ABI）是 Electron 专属值，用户机器上装的原生模块与它不匹配；
   ④ **耦合面**：把 CLI 行为与应用运行时绑成一体，升一个等于动另一个。
   （Electron 内置 Node 的具体版本号：**未确认** —— 不在本阶段核对。）
3. **否决：照 WorkBuddy 自建 COS binaries 分发。**
   理由：① **不解决任何问题**：自建渠道只是把上游产物换个地方放，**GPL 义务跟着二进制走、
   不跟分发渠道走**，义务一条不减；② **多一份缺口**：自建分发要回答"谁维护镜像、如何同步上游
   安全更新"，而 uv（GitHub release + sha256）与 nodejs.org 官方 dist 本身就是"版本钉死 +
   校验文件"的形态，复用即可；③ **多一份信任成本**：多一个自建域名/COS 就多一套凭证与审计面，
   而 spec 本轮明确先不做私有化镜像。将来内网/无外网要做的是**镜像官方产物**（并核 sha256），
   不是自建分发。
4. **否决：把 MinGit 当 `gitbash` 运行时用。**
   理由：两种变体都不含 `bash.exe`（标准版只有 `/bin/sh`，busybox 版是 `ash` 且实验性、不支持
   交互式终端）；拿它当 `gitbash` 就是名不副实。若最终产品只要"POSIX sh + 常用工具"而不是 bash
   语义，应另立一条决策重开本记录，而不是就地改口径。
5. **（暂不采纳）从 PortableGit 裁剪出"只要 bash"的极小子集。**
   理由：上游不支持裁剪 MSYS2 用户态（bash 与 `/usr` 布局、`/etc` 配置、`msys-2.0.dll` 强耦合），
   裁错就启动不了；且**裁剪不改变许可义务**（还是同一批 GPL 组件）。先按整包分发，
   裁剪留作阶段 2 的体积优化**实测项**，实测通过再单独记一条决策。
