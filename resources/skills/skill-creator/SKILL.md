# 技能脚手架

本技能回答一个问题：**在 KamiBuddy 里造一个技能，怎么写才算对。**

技能是数据，不是代码：一个技能 = **一个文件夹 + 里面的 `SKILL.md`**。
frontmatter 声明它叫什么、什么时候该用，正文是加载后要遵守的指令，文件夹里的其它文件按需加载。

## 一、SKILL.md 的骨架

```markdown
---
name: weekly-report
description: 把零散的工作记录整理成周报。当用户给出本周记录并要求「出周报」「汇总这周做了什么」时使用。
version: "1.0.0"
---

# 周报整理

## 红线
- 只依据用户提供的记录，不虚构未提到的数字与结论。

## 步骤
1. 通读记录，抽出「完成 / 进行中 / 阻塞 / 下周计划」四类。
2. 按下方格式写入工作空间，文件名 `周报-<YYYYMMDD>.md`。

## 输出格式
（要写成什么样，给模板）
```

正文只用三级标题分节，常见的四节是：**红线**（不许做的事）、**步骤**（按什么顺序做）、
**判据**（分支怎么选）、**输出格式**（交付成什么样）。

### frontmatter 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 技能名。就是 `/skill:<name>` 与 `use_skill` 的入参，也是导入后的目录名 |
| `description` | 是 | 触发依据（写法见 §二）。模型与技能页都只靠这一句判断「什么时候用你」 |
| `version` | 否 | 技能页展示的声明版本，三段式如 `"1.2.0"` |
| `user-invocable` | 否 | 可见性开关，见 §五 |
| `disable-model-invocation` | 否 | 可见性开关，见 §五 |

只有 `name` / `description` / `disable-model-invocation` 三个键是 pi 自己认的，
其余由 KamiBuddy 自己读（`user-invocable` 决定 `/` 菜单是否列出、`version` 供技能页展示）。
写别的键不会有任何效果 —— 从 WorkBuddy 搬进来的技能保留它们的 `category` / `tags` / `agent`
做溯源可以，自研技能不要写。

### 命名规则（与导入校验逐条一致）

- 只能用小写字母、数字、连字符：`^[a-z0-9-]+$`。大写、下划线、空格、中文都不合法，导入会被拒。
- 不超过 **64** 字符。
- 别用首尾连字符、也别出现连续连字符（`-a` / `a-` / `a--b`）——导入这一关不拦，但技能加载时
  会产生告警，直接避开。
- 名字要能一眼看出用途（`meeting-notes` / `weekly-report`），别用 `skill1` 这类占位名。

### 写法限制（导入校验用的解析器是真 YAML 的子集）

以下写法会**直接报错**，不是「将被忽略」：

- 一行只能是 `key: value`；数组写 `key: [a, b]`。
- **不要**写缩进列表或嵌套对象（`key:` 后跟缩进内容）——这是 WorkBuddy 风格的写法，我们读不了。
- 块标量只支持 `|` / `|-` / `>` / `>-`；`|+` / `>+` 会报错。
- 版本号写三段 `1.2.0`。写 `1.0` 会被解析成数字，读的时候类型不符。
- 描述较长或含特殊符号时可以用双引号包住（解析器会去掉外层引号）。

## 二、description 决定触发

系统提示词里的技能清单段**每轮常驻**，而它只含两样东西：`name` + `description`。
所以 description 是模型判断「现在该不该加载你」的**唯一**依据 —— 它写的不是「我是什么」，
而是「**什么时候**该用我」。

判据：把这一句单独拿给一个不知道上下文的人看，他能不能判断「现在该不该用它」。

| | 例子 |
|---|---|
| ❌ 名词说明 | 「帮助用户处理文档的技能。」——任何场景都说得通，模型等于没有依据 |
| ❌ 只写能力 | 「可以统计字数、检查错别字、生成目录。」——没说要输入什么、什么时候该用 |
| ✅ 触发条件 | 「把零散的工作记录整理成周报。当用户给出本周记录并要求「出周报」「汇总这周做了什么」时使用。」 |

- 把用户**会说的话**写进去（「出周报」「汇总一下」），触发才准。
- 一行写完，别用块标量写多行：它每轮都在上下文里，越短越省。但别短到丢掉触发条件 ——
  省下的几十 token 换一次「该用没用上」不划算。
- 上限 1024 字符（超出会告警）；空 description 的技能**根本不会加载**，导入时也会被拒。

## 三、三级渐进披露

| 层级 | 内容 | 何时进上下文 | 成本 |
|---|---|---|---|
| 1 | 清单段的 `name` + `description` | **每轮常驻** | 每个技能都要付，累计可见（技能页顶部有估算） |
| 2 | `SKILL.md` 正文 | 加载技能时整体读入（模型 `use_skill` 或用户 `/skill:<name>`） | 正文多长，一次加载就多贵 |
| 3 | `scripts/`、`references/`、`assets/` | 正文明确要求时才用 | 不读不花 |

推论：**触发条件写在 description（层级 1）→ 流程与红线写在正文（层级 2）→ 资料、模板、
重复劳动下沉到层级 3。** 正文里凡是「大段背景、长清单、示例集」，都该搬成 `references/` 里的
一个文件，正文只留「什么时候读它」。

## 四、三个子目录的分工

| 目录 | 放什么 | 判据 | 是否进上下文 |
|---|---|---|---|
| `scripts/` | 确定性重复劳动：统计、校验、批量转换、格式解析 | 同样输入永远同样输出；用自然语言描述会啰嗦，且模型每次写得不一样 | 不进（模型只读「怎么调用它」） |
| `references/` | 按需加载的资料：规范、术语表、反模式清单、长表格、示例集 | 篇幅大但只在某些分支才需要；全塞正文会拖慢每次加载 | 读的那次才进 |
| `assets/` | 进产物的素材：模板、样例文件、字体声明 | 它是被复制/填充进交付物的，不是给模型读的 | 不进 |

- **东西不多就别建目录。** 只有 `SKILL.md` 的技能是完全正常的（一段流程 + 一份输出格式就够了）。
  为了「看起来完整」建三个空目录只会误导后来的读者。
- `scripts/` 必须在正文里写清**用什么跑、依赖什么运行时**。能落进既有受控工具的活优先走工具
  （例：HTML→docx 的转换只许调 `docx_convert`，不许自己写脚本跑 python）—— 没有可用运行通道的
  脚本等于死代码。

## 五、两个可见性字段

两个字段互相独立，各自收一个入口；不写就是两边都可见。

| 字段 | 效果 | 什么时候该写 |
|---|---|---|
| `user-invocable: false` | 不出现在 `/` 菜单（仍留在模型清单里，仍能被其它技能按路径引用） | 用户不会主动调的内部能力技能（被某个大技能按路径调用的子技能） |
| `disable-model-invocation: true` | 不进模型清单段，`use_skill` 加载它会被拒绝（用户仍可手动 `/skill:<name>`） | 只该由用户显式发起、不该被模型自动挑中的技能 |

- 两个都写 = 纯内部技能：菜单里没有、模型也不自动加载，只能被别的技能按路径引用。
- **面向用户的技能两个都别写**（本技能 `skill-creator` 就是如此：用户能手动 `/skill:skill-creator`，
  模型也能自动路由过来）。
- `disable-model-invocation` 要慎写：它把技能从模型的视野里摘掉，模型就再也不会在你没料到的
  时候用它，且**不能**用删掉 description 来达到同样效果（那是死技能，连加载都不会发生）。

## 六、纪律

1. **不写死绝对路径。** 技能会被装到用户自己的技能目录，绝对路径在别人机器上一定错。
   同一个技能内的文件写相对 SKILL.md 的路径（`./references/anti-patterns.md`）；
   交付物路径写相对工作空间。
2. **不把大段文档塞进 SKILL.md 正文**（见 §三）。正文只留红线、步骤、判据、输出格式。
3. **一个技能只解决一类事。** 判据：新能力应该落成一个新的技能目录，而不是往同一个 SKILL.md
   里堆第 10 条规则 —— 正文越长每次加载越贵，触发也会变含糊。
4. **正文写给执行者，不写给读者。** 写「做什么、什么顺序、什么算完成」，不写背景铺垫与形容词。
5. **把「完成」写清楚**：产物落哪个路径、什么格式、回复用户时给什么（路径 + 要点 + 待确认项），
   别用「整理好」这种没有验收标准的说法。

## 七、闭环：造完怎么进系统

1. 产出技能目录：`<技能名>/SKILL.md`（带子目录的技能就把 `references/` 等一起放在同一层）。
2. 让用户导入 —— **技能页的「技能」页签 → 右上角「导入技能…」→ 选中含 SKILL.md 的文件夹**
   （技能页的侧栏入口是「专家·技能·连接器」，页签顺序是 专家 / 技能 / 连接器）。
   - 单个 `.md` 也能导入，但它**只复制那一个文件** —— 带 `references/` / `scripts/` / `assets/`
     的技能必须用文件夹导入。
   - 导入成功后**下一轮对话即生效**（技能清单每轮现读），不需要重启应用。
   - 高级出路：技能页「打开技能目录」把文件夹手工放进去也行（导入只是捷径）。但**不要绕开导入
     直接往技能目录里写文件**，除非用户明确要求 —— 导入是唯一的校验关卡，绕过去等于没有校验。
   - 技能的**发现只有一层**：技能目录下的每个一级子目录各算一个技能，嵌套在技能里的 SKILL.md
     不会被单独发现（`docx/typeset` 这类子技能就是被 `docx` 按相对路径读的）。要让一组能力
     各自可独立触发，就平铺成多个一级目录。
3. 自检（导入后请用户在一个**新会话**里试一次）：
   - 输入 `/`，技能菜单里有没有它（声明了 `user-invocable: false` 的技能按设计不出现）；
   - 输入 `/skill:<技能名>`，正文能不能展开；
   - 用一句该触发它的自然语言请求问一次，看模型会不会自动加载它（声明了
     `disable-model-invocation: true` 的技能不参与这一步）。

## 八、硬约束：导入失败要原样报出

导入失败时，**把导入接口返回的原始错误一字不改地贴给用户，并指出要改 SKILL.md 的哪一处**。

**不许只说「导入失败了」「名字好像有问题」** —— 用户看不到那句原始错误，你不说清楚他只能反复试。
报错里带 `<路径>:` 前缀的（frontmatter 解析类的还会带行号），把路径与行号一起转述。

| 原始错误（片段） | 要改哪里 |
|---|---|
| `技能名「X」不合法：只能用小写字母、数字和连字符（如 meeting-notes）` | frontmatter 的 `name` |
| `技能名过长（上限 64 字符）：X` | `name` 改短 |
| `SKILL.md 缺少 description —— 没有它模型无法判断何时使用该技能` | 补 `description`（写成空值等同于没写） |
| `frontmatter 缺少字符串字段「name」` | frontmatter 里补 `name` |
| `所选文件夹里没有 SKILL.md —— 技能必须包含 SKILL.md` | 选错目录了；技能文件必须叫 `SKILL.md`（大小写一致） |
| `请选择含 SKILL.md 的文件夹，或单个 .md 技能文件` | 选中的是文件但不是 `.md` |
| `技能「X」已存在。如需替换，请先到技能目录手动删除旧的（<路径>）` | 见下条 |
| `路径不存在` | 选中的路径已经不存在了，让用户重新选一次 |
| `无法解析的 frontmatter 行「…」，应为 key: value` / `「X」的值为空；本解析器不支持多行值` / `frontmatter 缺少结束的 --- 分隔线` | 按 §一的写法限制改 frontmatter |

- **重名当前不支持覆盖。** 要更新同名技能，先让用户到技能目录（技能页「打开技能目录」）删掉旧
  文件夹，再重新导入。**不要承诺「覆盖安装」**。
- 改完让用户**重新导入一次**再收工，不要假定改对了。
- 回复用户时给出「改了哪一处 + 为什么」的短句即可，别把整张表贴回去。
