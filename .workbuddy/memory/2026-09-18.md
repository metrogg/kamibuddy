## 团队协作七项能力对齐（spec: add-team-collaboration-parity，同日完成）

按 WorkBuddy 语义逐批复刻，**七批全部落地**（`.trae/specs/add-team-collaboration-parity/`）：

1. **共享任务列表**：新增 `core/team-tasks.ts`（TeamTaskBoard，纯逻辑）+ 
   `extensions/team-task-tools.ts`（create/update/list）。pending→ready→in_progress→
   completed/cancelled，上游完成**自动解锁**、上游取消**级联取消**；依赖只能在创建时声明
   且只能指向已存在的任务 → 天然无环。与 `todo_write` 无关（那是消息流投影）。
2. **单成员优雅关闭**：`team_shutdown { to, reason?, force? }` —— 默认投「收尾请求」，
   成员交回报告后 `closed` 并 dispose 宿主；force 才 abort。closed 成员在
   `resolveMemberSessions` 响亮拒绝（宿主已 dispose）。
3. **委派模式**：`team_delegate_mode` → `SessionHost.setDelegateMode` 把领导工具面
   收窄为 `DELEGATE_MODE_TOOLS`（协调/沟通/交付类），执行类全摘；与专家 extraTools
   正交（委派模式下 extraTools 也拿不回来）。
4. **计划审批**：`team_plan_review`（注册表记 `planStatus`/`planFeedback`，驳回必须给
   feedback）；裁决后**自动 team_send**。**未建成员侧 plan_submit** —— 我们的成员是
   fire-and-forget，没有「阻塞等批」状态（它这一轮产出就是提交物）。
5. **落盘**：新增 `core/team-store.ts`（`<configDir>/teams/<团队名>/config.json`，
   团队结构 + 任务板；团队名做路径安全校验）。`persistTeam` 挂在 emitTeamProgress +
   任务板写操作后（内容指纹比对，没变不写）；启动 `restoreTeamsFromDisk()`，
   成员一律按 closed + 「需重建」恢复。**未落盘信箱**（成员宿主不可恢复，
   消息没有可达收件人；成员产出已在领导会话 JSONL 里）。
6. **成员级模型**：`team_create` 的 `members[].model`，解析链
   成员显式 → agent.model → 领导模型，前两级不可用**响亮报错**；`team_status` 显示。
7. **成员审批归属**：`PermissionRequest.fromMember/fromTeam`，daemon 按成员 sessionId
   反查注册表注入，审批卡显示「来自成员「X」」。

工具面最终状态：`team-tools.ts` **七件套** + 任务板三件套（独立文件），
全部走 `agentTeamsEnabled` 开关 + craft 白名单 + `declareReadOnlyTools`。

### 经验（本批踩到的）

- **类型要先分清动作与结果**：`TeamPlanDecision`（approve/reject）与 `TeamPlanStatus`
  （approved/rejected）合成一个类型时，`reviewPlan(..., "approved")` 编译期合法、
  运行期莫名其妙 —— 是类型检查先抓到的。
- **对外一律给快照**：任务板曾直接返回板内对象引用，被测试抓到「隔空变异」
  （调用方持有的快照被后续状态迁移改写）。
- **落盘指纹别含时间戳**：`updatedAt` 每次都变，带上它等于缓存永不命中。
- **shell 写文件是雷**：用 `node -e` 写含反引号的 markdown，反引号会被当命令替换执行，
  把内容吃掉（本次把 spec 的修订段写坏过一次，靠截断重写修复）。写文档一律用
  Write/Edit 工具，别用 shell 拼接。
- **依赖门禁真会拦人**：任务板最初放 `src/daemon/`，被 extensions import 时
  `check:deps` 直接报违规 → 移到 `src/core/`。

## 七项之后的残留差距（核对 12-expert-teams.md 后盘点，2026-09-18 晚）

**P0 真差距（WorkBuddy 的硬要求，我们没做）**：**团队工具面按 `expertType` 联动**。
WorkBuddy `agent-teams-env.ts` 的 `resolveAgentTeamsEnv`：`expertType==="team"` →
**强制开启**（PRD 硬要求），否则按全局开关（默认禁）；env 变化还会触发 sidecar 重启。
我们 `isAgentTeamsEnabled()`（daemon/index.ts:2001）只读全局偏好 —— 后果两条：
①选了团队专家仍要手动去设置页开开关；②开关开着时**任何 craft 会话**都能建团（能力外溢）。
分析文档 §8.1 早就点名这条，上一轮只做了 expertType 字段 + 专家团页筛选，**工具面联动没做**。

**P1**：成员权限卡**按成员分组**（WorkBuddy 独立 `team-member-intercept-card`，
挂输入区上方与 sandbox 卡互斥同位；我们只有全局 modal 队列 + 归属标注）；
团队 UI 操作面（无任务面板/无 Ctrl+T；成员切换只有鼠标路径，**无 ↓ 切成员 / Ctrl+O 回领导**；
成员卡 / 实时计数行 / 点击聚焦查看都有 ✓）；专家包**安装链路**（WorkBuddy 有
expert-manager 的 init/register/validate/batch_create + `ensurePackageReady` 下载物化）。

**P2**：`expertType` 四值（WorkBuddy `skill|agent|plugin|team`，我们 `expert|team`）；
成员**轮次上限**（WorkBuddy agent frontmatter 有 `maxTurns`，我们只有 turns 统计）；
防幽灵成员三件套（provisional runtime → rekey → retireFailedTeamSpawn）；
truly-idle 收敛 + pending 落库（将来做自动化/后台委派才需要）；成员头像（源包 `avatars/` 没搬）。

**有意差异（不算落后）**：任务板不做成员自主认领（主理人指派，防成员误标完成）；
信箱不落盘；成员不做阻塞式等批；team_delete 走 abort（比 WorkBuddy「关闭较慢」快）。

**WorkBuddy 自认不做**：嵌套团队、领导角色固定、无会话恢复（/resume 不恢复成员）、
单会话单团队、权限在生成时确定（我们每次审批 → 更强）；它「任务状态可能滞后」
我们反而实时。

### 经验（UI 批次踩到的）

- **JSX 属性位置不能用 `{/* */}`**（那是 children 写法）：TS 报 `'...' expected`。
  属性位要用裸块注释 `/* */`。
- `bridge.ts` 是 **CRLF**，用 shell 的 `\n` 匹配多行会未命中 → 用单行正则
  `(\r?\n)` 或文件编辑工具。
- daemon 的 IPC handler 返回类型要求 `Promise` → 同步取数的 handler 也得写 `async`。
- 新样式一律用 token（`--space-*` / `--radius-*` / `--bg-*`），`check:tokens` 才不拦。
