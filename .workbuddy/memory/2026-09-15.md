## 调研：WorkBuddy 的「代码办公」与「日常开发」分界

结论（证据来自 `docs/workbuddy分析/02-prompts.md` §4.2 + §4.1）：

- **场景页签是空的区分。** `welcomemode` 下 code 与 work 的 `prompt.tpl`
  **逐字节相同**；工具白名单由 `workMode`（ask/craft/plan/expert）决定，
  不由 welcomeMode 决定。唯一历史差异是 CodeBuddy 时代的
  `workbuddy-craft-code-prompt.tpl` 多一条「产物回传小程序」条款，重构后已消失。
- **真正的分界线在「运行环境」这一层**：WorkBuddy 桌面（办公）vs
  CodeBuddy CLI/IDE（开发）共用同一个 CLI 内核，靠工具白名单 + 权限基线裁开。
  桌面端刻意不要：LSP、worktree、Notebook、checkpoint 回滚、Agent Teams、CI 集成、
  `/goal` 自治循环 —— 这些是 CLI 的产品位。
- 桌面端反而特有：present_files 双路交付、内联可视化（read_me/show_widget）、
  sites 发布公网链接、本地 Office 引擎。

## Worktree 任务隔离机制（`main/server.js` 的 WorktreeTaskDomain）

- **目录**：`~/WorkBuddy/Worktrees/<原仓库目录名>/<branchSlug>-<uid8>`
- **分支**：`workbuddy/<branchSlug>-<uid8>`
  - `slugifyBranch`：小写化 + 非 `[a-z0-9]` 全转 `-` + 去首尾 `-`
  - `uid` = `randomUUID().replace(/-/g,'').slice(0,8)`
- **RPC 9 通道**（`WORKTREE_TASK_RPC_CHANNELS`）：IS_GIT_REPO / LIST_LOCAL_BRANCHES /
  FETCH_BRANCHES / COUNT_WORKTREES / CLEANUP_WORKTREES / GET_WORKTREE_STATUS /
  CREATE_WORKTREE / DELETE_WORKTREE / CHECKOUT_BRANCH
- **createWorktree 失败回滚**：`removeWorktree` → `rm -rf worktreePath` → throw
- **checkoutBranch 的 dirtyPolicy 四态**：`abort`(默认) / `commit` / `stash` / `discard`
- **cleanupWorktrees**：跳过 `hasUncommittedChanges`、跳过近期（olderThanDays），
  只删 `workbuddy/` 前缀分支；返回五项计数器
- **阈值常量**：`WORKTREE_COUNT_WARNING_LIMIT = 25`、`WORKTREE_COUNT_CLEANUP_LIMIT = 50`
- **参数校验**：repoCwd / worktreePath 必须绝对路径，否则 throw
- **组件**（`packages/agent-ui/src/modules/worktree/worktree-chip.tsx`）：
  依赖 `useWorktreeGit`（isGit/branches/currentBranch/worktreeCount）、
  branch-list、cleanup-dialog、overlays、source-map

桌面端串联（`useCreateHomeTask`）：
1. 创建任务前若 `worktreeBaseBranch && cwd` → `createWorktree({repoCwd, baseBranch})`
2. 成功 → `cwd = worktree.worktreePath` + `recordWorktreeSource(path, sourceCwd, taskBranch)`
3. 失败 → toast `worktree.createFailedFallback`（warning），**降级用原目录继续**
4. 发消息前过 `useHomeBranchSwitchGate`：脏工作区弹 Modal 三选一（`BranchSwitchDirtyPicker`）

## 三个真踩到的坑（都有代价，别重犯）

1. **`validateWorkspacePath` 会拒掉副本路径** —— 副本在 `<配置目录>/worktrees/` 下，
   而该函数拒绝配置目录内的一切路径。不修的话副本会话 **resume 直接报
   「会话的工作目录不可用」**，功能等于不可用。修法：在配置目录那条规则里加
   `isWorktreePath(path)` 例外（只开副本根之内，配置目录本身照旧拒）。
2. **git 在 Windows 回报的 worktree 路径是正斜杠**（`C:/Users/...`），而
   `path.join` 给的是反斜杠。不 normalize 的话 cleanedPaths 与 WorktreeInfo.worktreePath
   「看起来相等却不等」—— 清理删对了文件，但所有路径比对静默失配。测试抓到的。
3. **本机 git 单次调用约 1–2 秒**（Windows + 杀软）：22 个用例跑了 180 秒，
   默认 5s 的 testTimeout 稳定误报。修法：文件级 `vi.setConfig({testTimeout: 60_000})`
   + `rm(..., {maxRetries: 10, retryDelay: 200})`（Windows 上刚跑完的 git 交句柄有延迟，
   直接 rm 撞 EBUSY）。

## 设计取舍（写下来免得后人改回去）

- **意图存 daemon 不存 renderer**：WorkBuddy 把它放在 home 组件 state 里，
  但那样切页面重建组件后，界面说「未启用」而新任务照样建副本。我们的
  `pendingWorktreeBranch` 是 daemon 模块级变量，并随 `workspaceSnapshot` 下发
  （与 current 同源，都是「下一个新任务怎么起」）。
- **新建任务不重置它**（与 defaultWorkspaceDir 相反）：空间选择在新建任务时清空是
  产品语义，副本开关是「我习惯在隔离副本里干活」的偏好，该沿用。
- **副本路径归任务区**：既避免以 `main-a1b2c3d4` 这种目录名进空间区成组，
  更要紧的是让 `isOwnedSessionDir` 为假 —— 「保存到工作空间」走新建目录的回退分支，
  **不会 rename 副本目录**（rename 会让 `.git/worktrees/` 指向不存在的路径，仓库半坏）。
- **v1 未做**：脏工作区切换门（`BranchSwitchDirtyPicker` 四态）、副本计数与清理界面入口
  （`cleanupWorktrees` 已实现但无 UI 调用点）、resume 后的 baseBranch/sourceCwd 还原
  （反推不出，按类型缺省）。

## 用户实测反馈：「切到代码开发什么都没变化」

**根因（查会话文件得到实证，不是猜）**：`~/.kamibuddy/sessions/` 最近几个会话的
cwd 都是 `C:\Users\wzd\KamiBuddy\2026-09-15-11-54-39` 这种**自动分配的时间戳目录**
（临时任务），不是 git 仓库。而原实现的门控是
`sceneId === "code" && cwd 非空` + 组件内 `isGitRepo` 判定 → **整块不渲染**，
所以切场景零视觉变化。

**教训（比 bug 本身重要）**：严格照抄 WorkBuddy 的「不可用就不渲染」在**我们的
默认状态下会命中盲区** —— 我们新建任务默认是临时任务（cwd 待分配/自动目录），
与 WorkBuddy 一样，但 WorkBuddy 用户多数会先选空间，于是它的隐藏策略不暴露问题，
我们暴露了。「功能存在但用户发现不了」等价于功能不存在。

**修法（最终采纳：对齐 WorkBuddy，不自行发挥）**：
先做了一版「始终渲染 + 不可用时在弹层说明原因」的有意偏离（`home-view` 只留场景
门控、组件三态、新增 `.ws-note`）。**用户随即要求回到与 WorkBuddy 一致的隐藏策略**，
已回退：

- `worktree-chip.tsx`：非 git 仓库 / 还没查完 → 返回 null（整块不渲染）；
- `home-view.tsx` 门控：`sceneId === "code" && cwd 非空`
  （对齐 WorkBuddy 的 `sceneMode === "code" && cwd`）；
- `index.css`：`.ws-note` 已删干净。

保留了一处与可见性无关的正确性改进：换目录时先 `setRepo(undefined)` 复位，
否则会短暂显示上一个目录的分支列表，用户可能按着旧列表选一个并不存在的分支。
（另：v1 那个 `cancelled` 守卫本来就有。）

**记一条判断依据**：可见性/交互策略一律**对齐 WorkBuddy，不自行发挥** ——
用户要的是复刻，不是改进。有偏离想法时先问，别直接做进代码。

## 字体调研（同日）

**我们**（`src/styles/tokens.css` 唯一真源）：

```css
--font-body: "PingFang SC", "MiSans", -apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", sans-serif;
--font-mono: ui-monospace, "Cascadia Code", Consolas, monospace;
```

MiSans **随包**（@font-face 在 `src/renderer/index.css`）。tokens.css 注释里的设计意图：
macOS 命中苹方；Windows 上苹方 / -apple-system / BlinkMacSystemFont 全不在 → 落 MiSans
（有真 400/600 字重，避免雅黑合成加粗发虚）；Segoe UI 与微软雅黑兜 MiSans 子集未覆盖的生僻字。

**WorkBuddy**：

- 随包字体 **Assistant**，4 字重（Regular / Medium / SemiBold / Bold）——
  `renderer/assets/Assistant-*-*.woff2`（证据：`docs/WorkBuddy-reference/asar-files.txt`）。
- Assistant 是 **Google Fonts 的希伯来-拉丁字体**（Adobe + Ben Nathan，OFL），
  语言支持只有 `hebrew / latin / latin-ext` —— **不含中文**，所以它的中文完全交给系统字体。
- 组件级普遍写 `font-family: var(--wb-font-family, "PingFang SC")`；
  **`--wb-font-family` 在所有已解包 CSS 里找不到定义处**（只有 var() 使用）。
- 等宽 `--wb-font-mono`；代码块 / 文件树 / markdown 编辑器用
  `--vscode-editor-font-family` / `--vscode-font-family`；登录页另用 Montserrat（营销页）；
  KaTeX 一整套（数学公式）。

**关键对比**：**随包方向相反** —— 我们随包**中文**字体（MiSans，解决 Windows 中文发虚），
它随包**拉丁**字体（Assistant，统一拉丁字形）。另外我们是**单点真源**
（DESIGN.md §2.6 强制，还专门修过「MiSans 声称已接实际没接」的账目错误），
它是**散装的**（变量只有使用没有定义，各组件各写 fallback）。

## 字体改回系统字体（同日，用户反馈）

用户反馈「MiSans 在一些电脑上发虚不清」，要求改回微软雅黑。已改（`src/styles/tokens.css`）：

```css
--font-body: "PingFang SC", -apple-system, BlinkMacSystemFont, "Segoe UI", "Microsoft YaHei", "MiSans", sans-serif;
```

MiSans 从第 2 位挪到**栈尾** → Windows 回到「拉丁 Segoe UI + 中文雅黑」。
同步更新了 `src/renderer/index.css` 的 @font-face 注释与 `resources/fonts/README.md`
（新增「当前状态」一节，保留「当初为什么随包」作为记录）。

**根因（值得记）**：MiSans 子集只有 **3876 字**（ASCII + GB2312 一级汉字），
生僻字**本来就落回雅黑** → 同一段落里 MiSans 与雅黑**混排**，字形粗细不匀；
加上它是随包 webfont，在 Windows 上缺系统字体那种 hinting，部分 DPI/缩放下发虚。

**取舍**：改回后 `font-weight: 600` 由雅黑**合成加粗**（雅黑无真 600 字重）——
这正是当初随包 MiSans 的唯一理由（见 resources/fonts/README.md）。用户选择清晰度优先。

**踩过的差点犯的错**：第一版我把 `"Microsoft YaHei"` 放在栈第 2 位，那会让 **Windows 上
的拉丁也用雅黑**（雅黑含拉丁字形，且排在 Segoe UI 之前）。原栈的意图是「拉丁 Segoe UI /
中文雅黑」，只是 MiSans 插在第 2 位把两者都盖住了 —— 所以正确改法是**把 MiSans 挪到末尾、
其余顺序不动**，不是把雅黑提前。

**未做（待用户定）**：MiSans 的 @font-face 与两个 woff2（共 951 KB）仍随包，现只作栈尾兜底、
几乎不命中。要不要清掉需单独决策。

**顺带发现（未动）**：`src/renderer/index.css` 里有 **19 处**等宽字体栈字面值
（`ui-monospace, "Cascadia Code", Consolas, monospace`），与 `--font-mono` 同值却没引用变量
—— 违反 DESIGN.md §2.6「不得就地写 font-family 字面值」，属既存技术债。

**排查手法记一笔**：判断「某功能为何不显示」时，**先读会话文件 header 的 cwd**
（`~/.kamibuddy/sessions/*.jsonl` 第一行），比问用户「你选目录了吗」快且准。
注意 `~/.kamibuddy` 是隐藏目录，Glob 工具默认不匹配它 —— 要写 node 脚本读。
