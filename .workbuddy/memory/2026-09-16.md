## 插入任务（steer）：功能早就接好了，但被会话互斥链吞掉（真架构 bug）

**用户报「agent 执行时再输入一条命令，界面没反应」**。排查结论分三层：

1. **pi 原生就有**，而且我们**早已接入**：`AgentSession.steer/followUp/clearQueue`、
   `PromptOptions.streamingBehavior`、`queue_update` → 我们的 `queue_changed`（带队列内容）。
   `session-host.prompt` 在 isStreaming 时默认 steer（`core/session-host.ts`），
   chat-view 的 placeholder 也写着「补充说明会插入当前任务…」。
2. **真凶在 daemon 的互斥链**：`[INVOKE.prompt]` 把每条消息 `enqueue(bucket, …)`，
   而链上前一个 prompt **await 的是整段 run** —— 第二条消息排在整轮后面，
   出链时流式已结束，steer 分支永远走不到，退化成「跑完后新一轮」。
   `whileStreaming` 参数实际是死代码。**修法**：`bucket.running` 时旁路直调
   `host.prompt(...)`（steer 是信号不是写操作，与 abort 同一条豁免理由）。
3. **反馈太弱**：发出去只有流末尾一行灰色「N 条消息排队中」。WorkBuddy 是
   **输入卡上方的排队 chip**（文本 + 编辑 + 删除）。

**配套改动**：

- `session-host`：①带 `whileStreaming` 的 prompt 撞上「run 恰好收尾」的竞态时，
  走 `AgentSession.prompt` 的 `streamingBehavior` 选项（消息不丢、不裸调被拒）；
  ②新增 `rewriteQueue(steering, followUp)` = `clearQueue()` + 按序重入队 ——
  **pi 只有整队清空、没有按条删除**，按条语义是这么合成的。两个代价（注释已钉）：
  clearQueue 只回文字 → 带图排队被删/编过一次后变纯文本；清空→重入队之间有
  无队列窗口，若 run 恰在此间收尾，消息挂队列等下一轮（不丢、chips 仍在）。
- 通道：`session:queue-rewrite`（ipc / bridge / preload 三层）。
- `shared/conversation.ts`：`queueCount`（纯计数）→ `queued`（内容数组，
  `QueuedMessages` 类型进 session-events），新增纯函数 `removeQueuedMessage`
  （摘**第一条**匹配、steering 优先、找不到原样返回供调用方跳过重排）+ 5 个用例。
- `chat-view`：计数行删除，输入卡上方渲染排队 chips（「待发送」徽标 + 文本 +
  编辑＝填回草稿并摘除 / 删除＝摘除，都走 rewrite）；`App.rewriteQueue` 接线。

**排查手法记一笔**：这轮最值钱的一步是「顺着 IPC 往下挖到互斥链」——
UI 层看是「没反应」，实际是消息被静默排到了几分钟后。判断「某条链路是否生效」，
要沿 renderer → ipc → daemon handler → session-host 全程走一遍，
**任何一环的排队/串行机制都可能让后面的分支变成死代码**。

## F5 hidden context 查证结论（2026-09-16）：可以开工，不卡 pi

用户问「hidden context 是什么」后要求查证。结论：

- **pi 有官方改写点**：`transformContext?: (messages: AgentMessage[], signal?) => Promise<AgentMessage[]>`，
  在 agent-loop 的 `streamAssistantResponse` 里**每次模型调用前**执行
  （README 数据流：AgentMessage[] → transformContext → convertToLlm → LLM），
  README 明说用途含 "inject external context"。
- **三个关键性质**（读了 agent-loop.ts:288-295 确认）：①返回值即入模内容，可增删改；
  ②**只影响本次调用**——transform 是局部变量，不回写 state.messages、不落会话文件
  （正是 hidden context 需要的「每轮重新拼、不持久化」）；③`AgentSession.agent.transformContext`
  直接暴露，我们在 `installRequestSnapshot` 已包过一层观测——同一链再包一层注入即可，
  顺序：pi 扩展链（inner）→ 我们的注入 → 快照（快照记注入后的真实入模，口径更诚实）。
- **注入体**：在最后一条 user 消息前 prepend `<system-reminder data-role="user-context">` 块
  （`UserMessage.content` 是 string，直接拼接；数组形态则插 TextContent）。
  WorkBuddy 同款标记与容器语义：user-context 常驻 / additional_data 压缩时可剥离，
  stage 分 first_turn / every_turn。
- **两条纪律**：钩子 must-not-throw（沿用快照的台账上报通道）；**注入内容按 run 冻结**
  ——每轮都变的时钟会从「最后一条 user 消息」处打断该 run 的提示词缓存（工具结果都在它后面）。

## 真机首轮反馈：sys=0 bug + 实际内容（2026-09-16 中午）

用户真机跑了任务诊断面板，两个反馈：

### Bug：分类里「系统提示词 ~0」（实锤 + 已修）

实证路径：事件日志里 `01a0a7b9` 会话**运行期** context_usage 是 `sys=7066`（正常），
**01:29 / 03:37 两次切回会话后**变成 `sys=0`。根因：**切回历史会话走 resume 建新桶**
（`systemPromptTokens` 默认 0），resume 建完宿主立刻补发 context_usage，而 compose
只在 `before_agent_start`（下一次发消息）才跑——补发时桶里还是 0，renderer「后到覆盖」
把运行期的正确值盖掉。台账快照一直带 systemSegments（13.4K 字符）证明 compose 本身
没坏，坏的只是 resume 桶没数据。
**修法**：resumeSession 在补发 usageDetail 前用同一条 `composeSystemPrompt` 现算一次
填桶（piContext 置空，与 prompt:preview 同口径，估算略低可接受）；`composeSystemPrompt`
的 piContext 参数改可选。**排查手法**：这类「显示 0」先分运行期/切换期两段看事件日志，
两段值不同 = 桶生命周期问题，不是计算问题。

### 功能：② 加「实际内容」两个折叠块

光有计数不够，用户要看实际内容。② 现在四个折叠块：
占用与分类（估算）/ 最近一次入模拆分（真实计数）/ **系统提示词全文**（prompt:preview
同一条组装路径按当前两轴现算，不含 pi 上下文段）/ **hidden context 注入块**（宿主
最近一次注入的全文，run 结束仍可看）。`Fold` 组件统一两种形态：children（已在手的
数据）/ onLoad（惰性取全文，首次展开才拉 IPC）。
- `session-host.peekHiddenContext()`：`lastHiddenContext` 与 pendingHidden 同时写但
  **agent_end 不清**（pendingHidden 是 run 期账，这个是展示语义）。

### 「hidden context 注入块」卡在正在读取（用户反馈，已修）

真机点击后永远「正在读取」。代码链路核对无误（preload/bridge/handler 三层齐全）——
**根因是 preload 不吃 HMR**：renderer 热更出了新的四个折叠块，但运行中的 preload
还是旧的（没有 `hiddenContext` 方法），`window.kami.hiddenContext()` 同步抛
TypeError，而 Fold 的 onLoad 没兜同步异常 → 永远 loading。
**修法**：`Promise.resolve().then(onLoad)` 过一层微任务，同步抛也落拒绝分支显示错误。
**教训**：改 preload / daemon 后说「重启」要说得更硬 —— HMR 让界面看起来是新的，
恰恰掩盖了 preload 是旧的；判断「是不是 preload 旧了」的口诀：**界面结构新、
新加的桥方法不可用 = preload 没重载**。

### 「还没跑过任何一轮」但明明跑了很多轮（缓存时效 bug，已修）

实证链：台账 12:56 / 12:57 两轮的**每一步**快照都带 hiddenContextChars=528（注入在跑）；
eventLog 里 `session:hidden-context` 只到达过 daemon **一次且无错误** → handler 正常
返回了 undefined → 是 renderer 把那次空结果**缓存住了**（Fold 只在「从未取过」时
fetch；用户重启后先点开折叠块，彼时 pristine 桶还没有宿主，空结果被钉死）。
**修法**：onLoad 型折叠块**每次展开都重拉**（注入块按 run 变化，缓存时效本身就是错的），
换会话由 resetKey 清态。**教训**：带时间语义的读数（「最近一次」）不许缓存首次结果；
「缓存节省一次 IPC」在诊断面板这种低频入口毫无意义，陈旧数据代价却很高。
