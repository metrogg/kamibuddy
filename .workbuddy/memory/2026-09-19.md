## 实测排障：gpt-researcher-team 团队「到中间没人接了」

用户实测 `research-ai-agent-pcb-eda`（gpt-researcher-team 建的队）时发现流程断在
Phase 3.1 之后。**结论：进程被中断，不是逻辑 bug。**

### 证据链

- **领导会话** = `2026-09-18T16-51-05-019Z_01a0b56d-c4b9-...jsonl`（80 KB，29 行）
  - `16:51:06` 用户提问 → `16:52:01` `team_create` 建 4 人团 →
    `16:52:07~16:52:09` 三个待命成员回投 → `16:54:26` 谭溯源交 Phase 1 初调 →
    `16:54:39` 领导派 Phase 3.1 给谭溯源（`deliverSessionMessage` 成功，
    会话里出现「已投递给：谭溯源」）→ `16:54:52` 领导发进度通报
  - **会话到此为止**。领导再没收到任何回投，也没再动过。
- **成员会话** = `..._01a0b56e-8c18-...jsonl`（699.9 KB，109 行）
  - `16:51:56` 起跑（任务 = Phase 1 初调）→ 50 次 `web_search` + 26 次 `web_fetch`
  - `16:54:21` 产出 Phase 1 摘要 → `16:54:39.903` 收到
    `[来自领导的消息] 【Phase 3.1 深度调研 · 单章深挖】`
  - `16:54:47~16:55:13` 补搜 4 处缺口 → `16:56:03.469` 产出
    「# Phase 3.1 章节草稿 …」**（生成中途被截断，还在 thinking 阶段就没了）**
  - `host.prompt()` 的 `.then()` 从未 resolve → `onComplete` 从未回调 →
    **回投根本没发生**
- **事件日志** `logs/events-2026-09-18.jsonl`：最后一条 `ts` =
  `2026-09-18T16:56:03.466Z`，即成员产出最后一字的那一刻。
  **daemon 之后再没写过任何事件** → 进程整体死亡（不是团队模块单独挂）。
- **团队注册表** `~/.kamibuddy/teams/research-ai-agent-pcb-eda/config.json`：
  谭溯源 `status: "idle"`、`turns: 0`、`toolCalls: 77`。
  注意 `turns: 0` 而 toolCalls 77 —— `turns` 只在 `assistant_done` 事件里 +1，
  而 `assistant_done` 发生在**整轮结束时**；草稿没写完就死了，所以永远是 0。
  这个计数器可以当「一轮是否真正收尾」的探针。

### 判定

**不是团队逻辑问题，是「一轮正常结束、但回投没发出去」。** 逐层证据：

1. **领导侧路径完全正常**：`deliverSessionMessage` 在 run 中走旁路，投递成功
   （领导会话里出现「已投递给：谭溯源」回执）。领导侧没有 bug。
2. **成员那一轮的 LLM 调用是成功收尾的**：最后一条消息
   `stopReason: "stop"`、`rawStopReason: "stop"`、`content: [thinking, text]`、
   草稿正文 **18,575 字符完整写完**（含「新增来源」「来源清单」段）。
   所以**不是**截断、不是崩在生成中。
3. **但 `onComplete` 没被调用**（`turns` 停在 0，领导侧零回投）。
   `member-runner.ts:201-213` 的形状是
   `void host.prompt(task).then(() => { ...hooks.onComplete(...) })` ——
   `.then()` 没跑，说明 `host.prompt()` 的 promise **没有 resolve**。
4. **进程级中断**：`logs/events-2026-09-18.jsonl` 最后一条 `ts` =
   `2026-09-18T16:56:03.466Z`（epoch ms），正好是成员产出最后一字那一刻，
   之后 daemon **再没写过任何事件**。而 16:56:03 那条还是
   `session_event`，不是 `run_finished` —— 这一轮的收尾事件也**没落盘**。

**结论**：应用在成员产出完毕、`host.prompt()` 即将 resolve 的窗口内被终止
（用户关闭应用 / 进程被杀 / 主界面已「已就绪」而团队会话未收尾）。
`host.prompt()` 的 promise 随宿主进程一起消失，`.then()` 永不执行，
回投自然发不出。领导侧因此在等待中静默。

**也就是说：这是「进程被杀」而不是「协作机制有洞」。** 但暴露了一个真实弱点 ——
**领导侧没有心跳/超时兜底**：成员一旦没有回来，领导就永久等待，界面上也没有
任何提示。这在 WorkBuddy 里同样存在，但值得作为 P2 加一层「成员超时未回投」
的可见性。

- **排查团队中断，先看事件日志的 `ts` 最大值** —— 它只由 daemon 写，

### 一、新增 `interrupted` 成员态（贯穿七层）

## 第二次复现 + 找到真凶：回投被 `void` 掉了（同日晚）

用户又贴了一张截图（团队 `research-ai-eda`），同一症状「所有人都没动静了」。
**这次现场比第一次干净得多，并推翻了第一次的两条结论。**

### 纠错一：`turns: 0` 不是「一轮没收尾」的信号，它恒为 0

`daemon/index.ts` 的 `onProgress` 接线把轮数增量**写死成 0**：

```ts
teamRegistry.recordProgress(leaderId, name, 0, text);  // ← 第三参恒为 0
```

而 `team-runtime.ts` 是 `member.turns += turnsDelta` → **注册表 `turns` 永远是 0**。
第二次复现的现场直接证死：`activity = 已完成 2 轮` 而 `turns = 0`（同源却对不上）。
第一次复现时我把 `turns: 0` 当成「`onComplete` 没跑」的铁证，**推错了方向**。
真正该看的是 `activity`。

### 纠错二：不是 `.then()` 没跑，是死在回投调用前的一瞬

第二次时间线（三方对账）：

| 时刻 | 事实 |
|---|---|
| `18:03:52.130` | 领导调 `team_send` 派 Phase 2 给季要纲 |
| `18:03:52.134` | `team_send` 返回成功 |
| `18:04:07.446` | 季要纲产出 **4,840 字完整 JSON 大纲**，`stopReason: "stop"` |
| `18:04:07.444/.445` | 两条 `team_member_progress` 落盘，`activity=已完成 2 轮` |
| 之后 | **事件日志彻底停止**；`logs/` 下**没有 `events-2026-09-19.jsonl`** |

`onComplete` 的执行顺序：

```
① markStatus(idle)                  —— 同步，落盘了
② emitTeamProgress()                 —— 同步，落盘了（事件日志停在这之后）
③ void deliverSessionMessage(...)    —— 异步 + 游离，从没执行
```

**进程死在 ② 与 ③ 之间。** `.then()` 跑了、`onComplete` 也跑了
（`activity=已完成 2 轮` 就是它写的），死的是它内部 `void` 掉的那个回投。

### 真凶：回投是唯一送达通道，却被 `void` —— 「同步的先落，异步的最后丢」

`markStatus`/`emitTeamProgress` 都同步完成所以落盘了；`deliverSessionMessage`
是异步（`enqueue` → `host.prompt` → 写会话文件）且被 `void`，不参与任何生命周期。

### 修复（批次 ③，已落地）

1. **先留痕再投递**：`onComplete` 拆成 ①`markStatus` → ②`markPendingDelivery`（同步，
   新增）→ ③`emitTeamProgress` → ④`await` 回投。② 先把「有一份产出待送达」同步
   落盘，进程死在 ③④ 之间也能在重启后看见「它跑完了、产出在会话记录里」。
2. **回投改 await**：`MemberHooks.onComplete`/`onFailed` 返回 `void | Promise<void>`，
   `member-runner.ts` 的 `.then()` 回调改 `async` 并 await；接线层不再 `void`。
3. **修 `turns` 恒定 0**：新增 `recordCompletion`（**赋值**而非累加），由 `onComplete`
   带权威轮数回填。
4. **回投失败补发通知**：失败时除了记 `team_member_delivery_failed`，还回投一条
   「产出回投失败，产出仍在会话记录里」——不让领导继续静默。
5. **UI**：`SubagentStatus` 加 `pendingDelivery` / `pendingDeliveryTurns`；
   状态栏摘要行优先级 **产出待捞 > 中断 > 工作中 > 平静**；chip 加 `.recoverable`
   琥珀描边；`deriveAgentRow` 的 pendingDelivery 分支优先于 interrupted 文案。

**刻意只存标记，不存产出正文**（用户拍板）：正文在成员会话 JSONL 里已有一份，
存进注册表是双写（违反 `core/run-ledger.ts` 的不双写纪律），且最长 24k 字符。

## 第三次复现：又一个全新根因 —— `await` 了「入队即返回」的 `followUp()`

用户第三张贴图（团队 `research-ai-agent-enterprise`），仍是「依旧直接没了」。
**这次 daemon 全程存活、进程没死**，前两次的解释完全套不上。

### 现场（三方对账）

| 时刻 | 事实 |
|---|---|
| `18:37:34.849` | 谭溯源回投 Phase 1 摘要（**回投成功**） |
| `18:37:43.783` | 领导派 Phase 2 给季要纲（投递成功） |
| `18:37:47.715` | 领导**开始流式输出进度通报**（会话最后一条，`stopReason:"stop"`） |
| `18:37:52.899` | 季要纲第 2 轮跑完（会话第 10 行是完整 3 章大纲 JSON），`onComplete` 触发回投 |
| ↑ | 领导**仍在流式** → 走 `isStreaming` 分支 → `session.followUp()` **入队即返回** |
| ↑ | `await` 立即 resolve → `finally` 的 `clearPendingDelivery()` **抹掉留痕** |
| 之后 | 那条回投只躺在 pi 队列里，**从未被消费**；领导会话再无写入 |

**事件日志 `18:37:52.898` 仍在写** → 不是进程崩溃（第二次的结论不适用）。

### 根因：pi 的 `followUp()` 是「入队即 resolve」

`agent-session.js` 的 `_queueFollowUp(text, images)` 全程同步：
`this._followUpMessages.push(text)` + `_emitQueueUpdate()` + `this.agent.followUp(...)`，
**不 await 任何东西**。d.ts 注释原文：

```
Queue a follow-up message to be processed after the agent finishes.
Delivered only when agent has no more tool calls or steering messages.
```

所以 `await host.prompt(composed, "followUp")` 的 resolve **只代表入队成功**，
而 `finally { clearPendingDelivery() }` 把它当成了送达回执 → **主动擦掉了痕迹**。
这次比前两次更隐蔽：前两次至少留痕，这次是自己擦掉的。

### 消费时机（精确信号，关键）

`agent-session.js` 的 `_handleAgentEvent` 里，`event.type === "message_start" &&
event.message.role === "user"` 时，先查 `_steeringMessages.indexOf`，再查
`_followUpMessages.indexOf`，命中则 `splice` 掉并 `_emitQueueUpdate()`。
**「待确认的正文不在队列里了」= 已送达，与消费同刻。**
`session-host.ts` 把 pi 的 `queue_update` 折成 `queue_changed`（1551 行附近），
已流到 daemon 的 `emitSessionEvent`。

### 修复（批次 ③.3）

- `session-host.prompt` 返回 **`{ queued: boolean }`**（`isStreaming` → true，
  另两分支 → false，后者是真进上下文 = 已送达）；新增 `getFollowUpQueue()` 透传
  `session.getFollowUpMessages()`（补「入队事件早于登记」的竞态）。
- `team-runtime` 新增 `deliveryAwaiting: Map<leaderId, Set<{memberName,text,seen}>>`。
  `markDeliveryPending(leaderId, name, text, alreadyQueued)` 登记（`seen` 初值）；
  `confirmDelivery(leaderId, queued)` 在每次 `queue_changed` 时按**两拍判据**销账。
- `deliverSessionMessage` 返回值改 `{ queued }`（两分支都透传）；
  `onComplete` 按 `result.queued` 分流：true → 登记待确认，false → 直接清标记。
- `emitSessionEvent` 挂 `queue_changed` → `confirmDelivery` → 有销账才刷投影。
- `member-runner.prompt` 显式丢弃返回值（否则 `Promise<{queued}>` 不能赋给 `Promise<void>`）。

### 两拍判据（**必须**，单测跑出来的）

「不在队列里」**≠**「已送达」—— 也可能是「从没进过队列 / 被 `clearQueue()` 丢掉 /
队列里是别的消息」。所以：**① 见过它在队列里（`seen`）② 然后它消失了** 才销账。
`clearQueue()` 是另一条丢失路径：pi 在用户中止时会把 `_followUpMessages = []`
并 `agent.clearAllQueues()`。

### 验证

`tsc --noEmit` 干净；5 个相关文件 **195 passed**；四项门禁全绿。

### 经验（三条，都是通用的）

1. **`await` 一个「入队即返回」的函数拿不到送达事实。** 要确认「对方真收到」，
   必须找**与消费同刻**的观测信号，不能拿 resolve 当回执。
2. **「不在队列里」≠「已送达」**，必须**先见过、再看它消失**（两拍）。
   单拍判据会误销账 —— 这是单测跑出来的缺陷，不是设计时想到的。
3. **失败路径上不要急着擦痕迹。** `finally { clearPendingDelivery() }` 在
   「操作本身不承诺结果」时是有害的：它把「可能没送达」粉饰成「已送达」。
   痕迹该由**确凿的成功信号**擦，不由**流程走完**擦。
4. 三次复现三个根因（`void` → 进程死在窗口 → 入队≠送达），**不要用一个解释套三次**。
